# 需求完整性与闭环逻辑

## 1. 需求完整性清单

每个功能需求必须覆盖以下维度。缺少任何维度表示需求不完整。

### 1.1 核心维度

| 维度 | 描述 | 验证方法 |
|---|---|---|
| **正常路径** | 正常路径 — 预期用户操作使用正确输入产生预期结果 | 测试用例必须存在并通过 |
| **空/无输入** | 无输入、空白字段或缺失参数 | 测试用例必须验证系统响应（错误消息 / 默认行为） |
| **无效输入** | 格式错误、超出范围、非法字符 | 测试用例必须验证拒绝或错误反馈 |
| **边界值** | 最小值、最大值、刚好超出上限、刚好低于下限 | 测试用例必须覆盖边界情况 |
| **错误反馈** | 操作失败时系统必须显示清晰、可操作的错误消息 | 错误消息必须可见、可读且准确 |
| **状态恢复** | 出错后用户可以重试或返回有效状态 | 测试用例必须验证恢复路径有效 |

### 1.2 认证与权限维度（如适用）

| 维度 | 描述 | 验证方法 |
|---|---|---|
| **未认证访问** | 未认证用户尝试访问时发生什么 | 必须重定向到登录页面或阻止访问 |
| **权限级别** | 不同角色的访问边界（管理员 vs 普通用户） | 测试用例必须验证每个角色边界 |
| **会话过期** | 令牌过期或无效会话的处理 | 测试用例必须验证重定向或重新登录行为 |

### 1.3 数据与状态维度（如适用）

| 维度 | 描述 | 验证方法 |
|---|---|---|
| **数据加载** | 数据获取期间的加载状态显示 | 加载期间必须显示加载指示器或骨架屏 |
| **空数据** | 无数据时显示什么（首次用户、清除数据） | 必须有回退消息或空状态 UI |
| **数据刷新** | 用户能否刷新或重新加载数据 | 刷新机制必须正常工作并更新显示 |

## 2. 闭环逻辑规则

闭环意味着每个用户操作都有完整的循环：**输入 → 处理 → 反馈 → 状态更新 → 下一个操作**。任何路径都不应让用户陷入困境。

### 2.1 操作-响应闭环

- 每次按钮点击/表单提交必须在 5 秒内产生可见响应
- 如果响应延迟（>1秒），必须显示加载指示器
- 如果响应失败，必须显示错误消息且用户必须能够重试

### 2.2 导航闭环

- 每个导航链接必须到达有效页面（无死链路由）
- 完成操作后，用户必须有明确的下一步（重定向、确认或返回链接）
- 任何操作都不应让用户停留在无法继续或返回的页面

### 2.3 数据生命周期闭环

- **创建** → 必须能验证创建的项存在
- **读取** → 必须准确显示数据，包括空状态
- **更新** → 保存后必须能看到更新的值
- **删除** → 必须确认删除且该项不再出现在列表中

### 2.4 错误恢复闭环

- 错误不能破坏页面（无崩溃、无空白屏幕）
- 错误不能损坏数据（之前的有效状态必须保留）
- 用户必须能够恢复：重试操作、修正输入或导航离开

## 3. 测试用例完整性验证

审查测试用例与需求时，应用以下检查：

### 3.1 覆盖矩阵

为每个需求填写此矩阵。任何 **MISSING** 单元格即为缺口。

```
需求：[名称]

| 路径类型       | 测试用例名称 | 状态 |
|-----------------|----------------|--------|
| 正常路径     | ?              | PASS / FAIL / MISSING |
| 空输入     | ?              | PASS / FAIL / MISSING |
| 无效输入   | ?              | PASS / FAIL / MISSING |
| 边界        | ?              | PASS / FAIL / MISSING |
| 错误反馈  | ?              | PASS / FAIL / MISSING |
| 状态恢复  | ?              | PASS / FAIL / MISSING |
```

### 3.2 闭环清单

对于每个涉及用户操作的测试用例：

- [ ] 测试是否验证操作产生了可见响应？
- [ ] 测试是否验证了异步操作的加载状态？
- [ ] 测试是否验证了操作失败时的错误消息？
- [ ] 测试是否验证了用户可以从错误中恢复？
- [ ] 测试是否验证了结果状态正确（数据/页面）？
- [ ] 测试是否验证了导航路径不是死链？

### 3.3 缺口严重程度级别

| 级别 | 定义 | 操作 |
|---|---|---|
| **严重** | 正常路径或错误恢复没有测试用例 | 发布前必须添加测试 |
| **高** | 无效输入或边界没有测试用例 | 发布前应添加测试 |
| **中** | 加载状态或空数据没有测试用例 | 建议添加 |
| **低** | 外观反馈或次要边界情况缺失 | 可选 |

## 4. 应用规则

在运行或编写任何模块的测试之前：

1. 将该模块的所有需求映射到 **覆盖矩阵**（3.1 节）
2. 对照 **闭环清单**（3.2 节）验证每个测试用例
3. 识别所有 **MISSING** 和 **严重/高** 级别的缺口
4. 在继续测试执行之前向用户报告缺口
5. 只有在用户确认缺口处置（添加测试 / 跳过 / 推迟）后才执行测试
