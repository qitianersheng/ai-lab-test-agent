## 1. 报告文件位置与命名

> **V0.12 · 默认只产 2 份**：① 主报告 `{任务}/{任务}-{env}.md`（仅 §2.1 概要 + §2.8 执行矩阵）② 缺陷报告 `{任务}/{任务}-缺陷报告-{env}.md`（§2.9，仅未通过）。下表的**历史归档 / `latest-{env}.md` 汇总 / 多任务合并 暂不默认生成**（模板保留，按需再开）。

**所有报告文件名必须包含环境标签**（local / SIT），从执行结果 `run.json` 的 `env` 字段（或 `run.json` 文件名的 ENV 段）读取。

> 范围边界：本框架仅支持 local / SIT。UAT 由业务方负责验收，**不会**也**不应**出现在执行结果或报告文件名中。

> 目录分层：**每个任务最近一次执行的产物**（当前报告 / Excel / 缺陷报告 / run.json / run.log / results.json）放
> `report/{任务}/`；历史时间戳副本统一归档到 `report/history/{任务}/`；`report/` 顶层只留
> `latest-{env}.md` 指针与 `_evidence/`（证据目录）——顶层不随执行次数堆积。

| 范围 | 文件名 |
|------|--------|
| 当前报告（任务目录，覆盖） | `/AI_LabTest/report/{任务}/{任务}-{env}.md`（env 小写；该任务最近一次的报告/Excel/缺陷报告/run.json 等都在 `report/{任务}/` 内） |
| 单任务历史归档 | `/AI_LabTest/report/history/{任务}/{任务}-report-{ENV}-{YYYYMMDD}-{HHMMSS}.md` |
| 多任务合并报告归档 | `/AI_LabTest/report/history/multi-report-{ENV}-{YYYYMMDD}-{HHMMSS}.md` |
| 各环境最新汇总（顶层，覆盖） | `/AI_LabTest/report/latest-{env}.md`（env 小写：local/sit） |
| 当前缺陷报告（任务目录，覆盖） | `/AI_LabTest/report/{任务}/{任务}-缺陷报告-{env}.md`（仅未通过用例，见 §2.9；历史归档同 `history/{任务}/`） |
| 证据截图 / 录屏 | 执行阶段 `browser_take_screenshot` 截图、（如 MCP 支持）录屏落盘，路径记于 `run.json` 各用例 `evidence` / `video` |

**示例**：
- `history/login/login-report-local-20260525-171042.md`
- `history/login/login-report-SIT-20260525-171825.md`
- `history/multi-report-SIT-20260525-180300.md`
- `latest-local.md` / `latest-sit.md`

**理由**：
- 同一天可能跑多次同一环境同一任务（调试场景常见），**时分秒后缀避免覆盖**（改进 3）
- 历史副本按任务归档到 `history/{任务}/`，顶层始终干净、只见「最近一次」，归档区按时间顺序排序清晰
- `latest-{env}.md` 始终是「该环境最新报告」指针，包含跳转链接
- 旧版本遗留在顶层的 `{任务}-report-*.md` 应迁移进 `history/{任务}/`（桌面应用在每次生成报告时自动迁移）

**时间来源**：从执行结果 `run.json.time`（ISO 时间）提取，**禁止用 `new Date()` 重新生成**（确保报告时间 = 执行时间）。提取方式：

```js
const iso = runJson.time;                       // "2026-05-25T17:10:00Z"
const date = iso.slice(0,10).replace(/-/g,''); // "20260525"
const time = iso.slice(11,19).replace(/:/g,''); // "171000"
const filename = `${module}-report-${ENV}-${date}-${time}.md`;
```

## 2. 必含章节

> **主报告默认只含 §2.1 概要 + §2.8 执行矩阵**（其余 §2.2–§2.7 暂不输出，模板保留备用）；§2.9 缺陷报告是**独立文件**。

### 2.1 概要

报告**第一行**必须明示环境（用于一眼定位）：

```markdown
# 测试报告 — {任务} — {ENV} — {YYYY-MM-DD}

> **环境**：local（http://localhost:5173）| SIT（{url}）
> **测试账号**：{username}（{role}）

## 概要

| 指标 | 数值 |
|------|------|
| 环境 | local / SIT |
| 前端 URL | {frontendBaseUrl} |
| API URL | {apiBaseUrl} |
| 总测试数 | X |
| pass | X |
| fail | X |
| partial | X |
| blocked | X |
| — 其中功能验证用例 | 共 A：pass / fail / partial / blocked |
| — 其中回归基线用例（仅锁现状） | 共 B：无回归 / 出现回归 |
| 功能验证通过率 | 功能验证 pass ÷ A（**回归基线不计入**） |
| 执行通过率（参考） | pass ÷ 总（含回归基线，不代表功能正确） |
| 执行时间 | Xs |
| 执行模式 | headed / headless |
| 报告时间 | YYYY-MM-DD HH:mm |
```

**通过率铁律（承接 test-case-completeness.md §1.6）**：回归基线用例（预期依据 = 现状锁定）的 pass **只代表「与现状一致、无回归」，不代表功能正确**。因此「功能验证通过率」只用功能验证用例计算，回归基线**不计入**；含回归基线的「执行通过率」仅作参考。一个任务若全部为回归基线用例，功能验证通过率记 `N/A（仅锁现状）`，**不得**报「100% 通过」。

**禁止**：环境字段使用「未知」或留空。如读不到执行结果 `run.json` 必须中断报告生成，提示用户先跑 `/ai-lab-test-execute`。

### 2.2 任务结果

```markdown
## 任务结果

| 任务 | 总计 | pass | fail | partial | blocked | 通过率 |
|------|------|------|------|---------|---------|--------|
| login | 14 | 14 | 0 | 0 | 0 | 100% |
| daily-practice | 12 | 10 | 1 | 0 | 1 | 83% |
```

> 「通过率」列口径见 §2.1，默认指**功能验证通过率**（回归基线不计入）。任务若含回归基线用例，在通过率后括注，如 `100%（功能验证）｜+3 回归基线仅锁现状`。

### 2.3 失败明细

```markdown
## 失败明细

### TC-{任务}-{编号}：{测试名}

**任务**：{任务名}
**状态**：fail | partial | blocked
**分类**：应用 bug | 测试 bug（误报） | 环境问题 | 路径不可建立 | flaky
**错误**：{错误消息摘要}

**备注（三段式 — 强制）**：
1. **做了什么**：{执行/尝试的步骤}
2. **看到了什么**：{实际观察到的可见结果}
3. **为什么足以关闭为 {状态}**：{结论的依据}

**截图**：`run.json` 该用例 `evidence` 中的截图路径（执行阶段 `browser_take_screenshot` 落盘）

**处理建议**：
- 如分类为「应用 bug」→ 创建 BUG-{ID}，**交开发处理**（不在报告内提议修复方案）
- 如分类为「测试 bug」→ 修复后已重跑（标注是否成功）
- 如状态为 blocked → 列出阻塞根因，环境解除后重跑
- 如状态为 partial → 列出已验证部分 + 保留部分 + 保留原因

**边界**：处理建议只写「应该走什么流程」（建 BUG 单 / 重跑 / 调整用例），
        **不写**「应该改 src/X.ts 第 Y 行」「推荐用 Z 方案修复」这类技术决策——属开发范畴。
```

**示例 — pass 备注（用于覆盖矩阵的「为什么算 pass」）**：
1. 用 yeqb001/123456 提交登录表单
2. URL 跳到 `/daily-practice`，localStorage 出现 `xiuxin-auth-storage`，token 字段非空
3. 满足 TC-login-001 全部断言 → pass

**示例 — blocked 备注**：
1. 用种子账号 yeqb001/123456 尝试登录
2. 14 条全部 401「服务器内部错误」，后端日志显示 `ECONNREFUSED 127.0.0.1:3306`
3. MySQL 未启动，登录路径根本未建立 → 全部 blocked，非应用 bug；DB 启动后重跑可解

**禁止**：模糊措辞（「疑似」「可能」）、无证据的后端猜测、把缺数据/缺入口笼统写成权限问题。

### 2.4 需求覆盖矩阵

按任务、按需求维度展开：

```markdown
## 需求覆盖

### 任务：{任务名}

| 需求 ID | 正常 | 空 | 无效 | 边界 | 错误 | 恢复 | 鉴权 | 数据 |
|---------|------|------|------|------|------|------|------|------|
| REQ-login-001 | PASS | PASS | PASS | MISSING | PASS | PASS | N/A | N/A |
| REQ-login-002 | PASS | PASS | FAIL | MISSING | PASS | PASS | PASS | N/A |
| REQ-record-003（仅现状锁定） | LOCK | LOCK | MISSING | MISSING | LOCK | MISSING | N/A | PASS |
```

**状态符号**：
- `PASS`：用例已实现且通过
- `FAIL`：用例已实现但失败（行为与预期相反）
- `PARTIAL`：部分断言已验证，另一部分被有意保留（备注必须说明保留哪部分及原因）
- `BLOCKED`：路径无法真实建立（备注必须给出阻塞根因，如缺数据/缺账号/缺外部依赖）
- `MISSING`：未实现该维度的测试用例
- `LOCK`：该维度仅由回归基线用例覆盖（预期依据 = 现状锁定）—— 已锁定现状但**未验证对错**，不等于 PASS
- `N/A`：该需求不涉及此维度
- `SKIP`：用户明确选择跳过

- 「期望行为 / 验收标准」必须**可复验**（重新怎么做、值应是多少），禁用「疑似」「可能」类模糊词。

## 4. 可追溯性要求

报告中每条记录必须能追到上游：

```
测试报告条目
  → 执行结果（run.json 中的逐条用例状态）
  → 测试用例 ID（TC-{任务}-{编号}）+ 验证性质（功能验证 / 回归基线）+ 预期依据
  → 需求引用（用例「需求引用」列：用户需求文档的 REQ-ID / 章节、会话提炼需求条目编号、或用户提供的用例编号）
  → 预期依据（用户需求文档 / 会话提炼需求 / 用户提供用例 / 现状锁定）
```

如果中间任何一环断了，必须在报告中标注 `LINEAGE_BROKEN` 提醒用户。

> 注：上表『预期依据』是**输入来源**粒度；用例「需求引用」列内的**细粒度取值**见 `test-case-completeness.md §1.6`（`PRD / 设计稿 / API契约 / 产品确认 / 会话提炼需求 / 现状锁定`）。

**预期依据一致性校验**：若某用例 `预期依据 = 现状锁定`（照抄 UI 现状）却标 `验证性质 = 功能验证`，必须能查到用户 / 产品对「应然行为」的显式确认依据（升级条件见 test-case-completeness.md §1.6）；查不到则标 `依据未核实`，该用例的 pass 在本报告按回归基线口径处理（不计入功能验证通过率）。

## 5. 报告生成时机

| 触发 | 行为 |
|------|------|
| 步骤 2 执行完成（成功） | 生成完整报告 |
| 步骤 2 部分失败 | 仍生成完整报告 |
| 步骤 2 异常中断（环境/超时） | 生成部分报告，标注 `EXECUTION_INTERRUPTED` |
| 用户主动要求 | 基于上次执行结果重新生成 |

## 7. 报告呈现给用户

报告生成后，**最后必须向用户口头汇报**以下三件事（**有 fail 时再加第 4 条**）：

1. **结果总览**：pass / fail / partial / blocked 的数量；**分别报「功能验证通过率」与「执行通过率」**，并点明回归基线用例只锁现状、不代表功能正确（口径见 §2.1）
2. **风险点**：应用 bug 数 + 高严重度 bug ID（**仅事实通报**，不评估是否影响发布）
3. **测试侧下一步**：以**陈述句**列出测试范畴的后续动作（补用例 / 调整执行 / 重跑特定用例）
   - **不**包含：bug 修复方案、修复优先级、发布与否、责任人指派
   - **不要**以问题形式追问用户决定
4. **（仅当有 fail）缺陷报告确认 + 修复去向**：提示用户「已生成缺陷报告，含 N 个应用缺陷（TC-…），请查阅确认；**如需修复，建议新开一个对话窗口进行**——本 QA 流程零源码修改、不在此会话改代码」。**陈述式提示即可，不用 `AskUserQuestion`、不追问、不等回复。**

不要让用户自己去翻 `.md` 文件才能知道结论。

## 8. Step 3 禁止事项（终态原则）

报告生成阶段是 3 步流程的**终态**，必须遵守：

| 禁止 | 原因 |
|------|------|
| **禁止在 Step 3 中发起用户问询** | 用例在 Step 1 已经确认，Step 2-3 是自动执行链。失败、bug、缺口都应在报告中陈述清楚，由用户读完报告后自行决定下一轮做什么 |
| 禁止以「请你裁定」「请选择 A/B/C」等方式索取用户选项 | 同上。报告是产物，不是问卷 |
| 禁止暂停等待用户回复后再写报告 | 报告必须一次性产出，包含全部失败分类、根因、建议 |
| 禁止用「待用户确认」占位符 | 失败分类必须明确给出（应用 bug / 测试 bug / 数据错误 / 环境问题等），不留 TBD |
| **禁止建议 bug 修复方案** | 报告只列 bug 事实（ID / 严重 / 描述 / 重现）；怎么修、改哪文件、用什么方案——属开发决策范畴，QA 不越界 |
| **禁止建议发布与否** | 「必须修复后再发」「可以带 bug 发布」属产品决策，不在报告范围 |
| **禁止指派责任人** | 报告陈述「待开发处理」即可，不点名「分配给 @某某」 |
| **禁止评估 bug 修复优先级** | 「P0 必须修」「P2 可推迟」属产品/项目管理决策 |

**正确做法（陈述式）**：
> TC-login-001 失败，分类为「测试用例数据错误」。
> 建议：核对用例文档第 23 行密码是否为预期值；若是手误，下轮可恢复为 123456 后重跑。

**错误做法（问询式）**：
> ❌ TC-login-001 失败，请从以下选项裁定：A. 改回密码 B. 改 DB ...

如果失败需要用户做出关键决策，做法是：**写完报告 → 口头汇报 → 由用户主动发起下一轮（新对话或新指令）**，不是在报告流程内追问。

> **有 fail（应用缺陷）时**：口头汇报里**陈述式提示用户确认缺陷报告**、并建议「**如需修复请新开一个对话窗口**」——修代码属开发范畴，**绝不在本 QA 会话内进行**（零源码修改铁律）。这是**陈述式提示**，仍不发起 `AskUserQuestion`、不追问、不等回复，**不违反终态原则**。

## 9. 可选交付物（XLSX / DOCX）

**默认交付物保持 Markdown 不变**。用户明确要求时（对接外部 QA 平台 / 汇报会议 / 跨团队归档），额外生成：

| 格式 | 用途 | 触发短语示例 |
|---|---|---|
| **XLSX 执行矩阵** | §2.8 执行矩阵的 xlsx 版（用例 12 列 + 执行 5 列），列与 Markdown 执行矩阵一致 | 「出 Excel」「出矩阵」「导出 xlsx」 |
| **DOCX 汇总报告** | 章节：元信息 → 闭环汇总 → 主要缺陷（fail） → 主要阻塞（blocked）→ 核心证据截图 → XLSX 引用 | 「出 Word」「出 DOCX」「导出报告文档」 |

**实现**：复用 Claude Code 自带 skill：
- `anthropic-skills:xlsx` — 生成执行矩阵
- `anthropic-skills:docx` — 生成汇总报告

**位置与命名**：与 Markdown 报告同目录、同命名规则：
- `/AI_LabTest/report/{任务}-report-{ENV}-{YYYYMMDD}-{HHMMSS}.xlsx`
- `/AI_LabTest/report/{任务}-report-{ENV}-{YYYYMMDD}-{HHMMSS}.docx`

**不主动生成的理由**：避免每次跑完都产出三份重复信息；按需输出可控成本。

**约束**：
- XLSX/DOCX 的内容必须**来源于已生成的 Markdown 报告**，不允许重新跑测试或重新分类
- 状态列、备注、证据引用要与 Markdown 完全一致，禁止改写

## 10. 经验回写到 site-patterns（Step 3 末尾强制）

报告生成完成后，**强制**扫描本轮产物提取已验证事实，增量写回 `AI_LabTest/site-patterns/{domain}.md`。这是 Step 3 的最后一个动作，没做完不算 Step 3 结束。

### 10.1 触发时机

Step 3 报告 Markdown 文件落盘后立即触发；XLSX / DOCX 生成（如有）之前。

### 10.2 候选事实来源（仅以下 4 类可沉淀）

| 来源 | 提取规则 | 例 |
|---|---|---|
| **功能验证 pass 用例** | 用例覆盖的可见行为（UI 文案、跳转目标、loading 状态、断言要点）；**仅限 `验证性质 = 功能验证` 的 pass** | 「登录按钮 loading 时文本变 Loader2 图标」（来源 TC-login-010 功能验证 pass）|
| **blocked 已确认根因** | 经排查并验证的环境/依赖事实 | 「MySQL 未启动 → /api/auth/login 返回 500 ECONNREFUSED」（来源本轮 blocked 排查）|
| **用户在 Step 1 用例设计中确认** | 用户提供 / 确认的需求条目 | 「确认无『记住我』『验证码』『忘记密码』功能」 |
| **用户在 Step 2 健康端点确认** | 已写入 environments.json 的端点真实来源 | 「健康端点 /api/health 来自 api/app.ts:42」 |

### 10.3 禁止沉淀

| 类型 | 原因 |
|---|---|
| **fail 用例的现象** | 这是 bug 不是事实；归属 Bug 清单 + 待开发修复 |
| **测试 bug 的修复笔记** | 归属 testCase（`{任务}-testcase.md`），不在 site-patterns 沉淀 |
| **推测性结论**（「可能」「应该」「疑似」） | 违反「只记录已验证事实」原则 |
| **partial 中间态** | 还没闭环，不算已验证 |
| **flaky 用例的偶发表现** | 不稳定，不构成事实 |
| **回归基线 pass 的现状** | 预期依据 = 现状锁定，只锁了「现在是这样」、未验证「应该是这样」，沉淀会让未确认的现状冒充已验证事实（见 test-case-completeness.md §1.6） |

### 10.4 增量格式

`site-patterns/{domain}.md` 文末维护「变更日志」节，每次 Step 3 追加一段：

```markdown
## 变更日志

### {YYYY-MM-DD} — 任务「{任务}」（{ENV}）

**新增事实**：
- {事实描述}（来源：{TC-ID pass | blocked 排查 | Step 1 用例设计确认 | Step 2 确认}）
- ...

**更新事实**：
- {旧事实} → {新事实}（来源：...）

**作废事实**：
- {旧事实}（作废原因 + 替代指针 → §X.Y）
```

### 10.5 去重 / 冲突 / 过时

| 情况 | 处置 |
|---|---|
| 候选事实与文件主体已有事实**主语相同、内容一致** | 静默跳过，不重复记录 |
| 候选事实与已有事实**冲突**（如换了端口/换了文案） | 不自动覆盖，在「变更日志」标 `CONFLICT_PENDING`，写入两份对照，由用户裁决 |
| 已有事实**过时**（如本轮验证发现废弃） | 主体保留但标 `DEPRECATED {日期}`，移到「已作废」子节，附替代指针 |
| 文件不存在 | 用 `_template.md`（如有）或最小骨架自动初始化，再追加变更日志 |

### 10.6 操作步骤（伪代码）

```
1. 读 site-patterns/{domain}.md，提取主体所有事实主语（用于去重）
2. 扫描本轮报告：功能验证 pass 用例清单（排除回归基线）/ blocked 根因 / Step 1 用户确认条目 / Step 2 健康端点确认
3. 按 §10.2 规则提取候选事实
4. 按 §10.3 过滤禁止项
5. 按 §10.5 去重 / 标冲突 / 标过时
6. 在文件末尾「变更日志」节追加一段（按 §10.4 格式）
7. 在终态汇报中告知用户：「site-patterns/{domain}.md 新增 N 条事实 / 标记 M 条冲突」
```

### 10.7 反约束

- 不允许跳过经验回写直接结束 Step 3
- 不允许把回写写到 Markdown 报告里（报告是结果快照，site-patterns 是长期记忆，分开）
- 不允许在 Step 1-2 中途回写（Step 3 是唯一沉淀点）
- 即使本轮没有新事实可沉淀，也要在变更日志追加一段说明：「{日期} — {任务}：无新增事实」
