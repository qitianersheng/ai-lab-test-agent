# 自动化测试工作流（3 步）

本文档定义了 AI_LabTest 的强制工作流。任何被加载到 Claude Code 的项目，只要复制本目录（`/AI_LabTest`）并按 `CLAUDE.md` 的指引引用规则，即可按本流程运行。

**铁律**：3 步必须严格按顺序执行。Step 1（用例设计）未通过用户门控时，不得进入 Step 2。

> **V0.4 变更**：剔除「代码库分析 / 需求分析 / 需求评审」三步。**测试用例设计**直接以用户提供的需求文档或用户直接给的测试用例为输入，不再做代码库扫描、三级回退需求发现、4 维度评审。流程由 6 步精简为 3 步。
> **V0.3 变更**：取消旧「测试脚本生成」步（不再生成 `.spec.ts`）。测试用例（Step 1 产物）直接交给 AI——AI 通过 Playwright MCP 浏览器工具**实时驱动浏览器**逐条执行用例、对照「预期结果」自判四态。

---

## 流程总览

| 步骤 | 名称 | 用户门控 | 输出位置 |
|---|---|---|---|
| 1 | 测试用例设计 | 是（确认用例） | `/AI_LabTest/testCase/{模块}-testcase.md` |
| 2 | 测试执行（AI 实时驱动 Playwright） | 否 | 结构化执行结果 `/AI_LabTest/report/{模块}-{ENV}.run.json` + 证据截图 |
| 3 | 测试报告 | 否 | `/AI_LabTest/report/{模块}-report-{ENV}-{YYYYMMDD}-{HHMMSS}.md` |

---

## 步骤 1 — 测试用例设计

**目标**：基于用户提供的输入设计测试用例，对照 `rules/test-case-completeness.md` 验证。

**输入来源（V0.4 · 用户驱动，二选一）**：

| 来源 | 处理 | oracle 默认 |
|---|---|---|
| **用户提供需求文档**（路径 / 粘贴文本：PRD / 设计稿 / 接口契约等） | 为「需求 × 适用维度」逐格设计用例 | 功能验证（应然） |
| **用户直接提供测试用例**（清单 / 表格 / 描述） | 结构化、补齐必填字段、对照完整性矩阵核验缺口 | 沿用用户标注；未标则按 §1.6 判定 |

> 不再做代码库分析、三级回退需求发现、4 维度需求评审。若用户既无需求文档也无现成用例，提示其先提供其一；**不**自行从代码反推需求。照抄当前 UI 现状得到的预期只能标 `回归基线`（见 `test-case-completeness.md §1.6`）。

**操作**：

1. 向用户索取并读取需求文档**或**现成测试用例。
2. 为每个「需求 × 维度」组合生成测试用例条目（用户直接给用例时则结构化并补齐字段）。
3. 每个测试用例必须包含：

   | 字段 | 说明 | 必填 |
   |---|---|---|
   | ID | `TC-{模块}-{编号}` | 是 |
   | 模块 | 所属模块 | 是 |
   | 用例类型 | 覆盖维度（见 `test-case-completeness.md §2.1`） | 是 |
   | 目的 | 测试验证什么 | 是 |
   | 前置条件 | 操作前所需状态 | 是 |
   | 测试操作 | 具体用户操作（按步骤拆分，与预期 1:1） | 是 |
   | 预期结果 | 可观察的结果（每条以【检查点类别】开头） | 是 |
   | 预期结果来源（oracle） | 预期依据来自哪里 + 验证性质（功能验证 / 回归基线） | 是 |
   | 清理 | 状态重置 | 如需要 |

4. 对照完整性规则核验：结构 / 覆盖 / 断言 / 隔离 / **顺序** / **数据** / **权限**
5. 用例执行顺序按 `test-case-completeness.md §6` 排序（主流程 → 同页面 → 依赖前置 → 同账号 → 只读靠后）；CRUD 链路按序组织
6. 涉及数据创建的用例按 `test-case-completeness.md §7` 维护数据追踪（`auto-uitest-{时间戳}` 前缀 + 「先复用再最小构造」原则）
7. 多角色用例按 `test-case-completeness.md §8` 用隔离会话同路径比较，禁止根据角色名推断

**用户门控**：
- 将完整用例清单呈现给用户
- 缺口处置（添加 / 推迟 / 跳过）由用户确认
- 若本批用例**全部**为「回归基线」（oracle = 现状锁定），额外提示「这些用例只锁定现状、不验证正确性，是否补充权威需求来源（PRD / 产品确认）？」

**产物**：`/AI_LabTest/testCase/{模块}-testcase.md`（含数据追踪，如适用）。

## 步骤 2 — 测试执行（AI 实时驱动 Playwright）

**目标**：把已批准的测试用例**直接交给 AI 执行**——AI 通过 Playwright MCP 浏览器工具实时驱动浏览器逐条执行用例，对照「预期结果」自判四态，捕获证据。**严禁在执行阶段修改源代码**（详见 `rules/test-execution.md`）。

**入口硬校验**：`/AI_LabTest/testCase/{模块}-testcase.md` 存在且非空，否则退回步骤 1。

**操作**：

1. 完成环境预检（白名单仅 `local` + `SIT`；询问用户目标环境；探活被测地址；详见 `test-execution.md §0`）。
2. 选执行模式：**可见**（有头浏览器，操作肉眼可见）/ **后台**（无头，更快）。
3. Read `/AI_LabTest/testCase/{模块}-testcase.md`，逐条用例：用浏览器工具（navigate / click / type / fill_form / snapshot / wait_for / take_screenshot）满足前置条件（如登录）→ 执行测试操作 → 对照「预期结果」判定四态。
4. **四态自判**（详见 `test-execution.md §2`）：
   - `pass`：预期可观察结果完全出现
   - `fail`：预期明确未出现且可复现（疑似应用缺陷，保留事实、不放水）
   - `partial`：部分满足 / 用例被部分跳过
   - `blocked`：前置/路径/登录态无法建立、依赖或地址不可达——**不是应用 bug**
5. 每条用例截图留证；落盘逐条结果，归约为结构化 `run.json`（四态计数 + 逐条状态 + 证据路径）。

**产物**：`/AI_LabTest/report/{模块}-{ENV}.run.json`（结构化执行事实，供步骤 3 报告消费）+ 证据截图。

---

## 步骤 3 — 测试报告生成

**目标**：按 `rules/test-report.md` 生成结构化报告。

**报告必含章节**：
- 概要（总数 / pass / fail / partial / blocked / 时间）
- 模块结果
- 失败明细（应用 bug / 测试 bug / 环境问题 / 路径不可建立 / flaky）— 备注按三段式
- 需求覆盖矩阵
- 覆盖缺口
- 应用 Bug 清单（**仅事实通报**：ID / 严重 / 模块 / 用例 / 描述 / 状态）
- 测试侧后续动作（补用例 / 调整执行 / 重跑 / 推迟覆盖）— **禁含** bug 修复方案、修复优先级、发布与否

**经验回写（Step 3 末尾强制）**：
报告生成完成后，按 `rules/test-report.md §10` 把本轮已验证事实增量写回 `AI_LabTest/site-patterns/{domain}.md` 的「变更日志」节。
仅沉淀已验证事实（来自功能验证 pass 用例 / blocked 已确认根因 / 用户在用例设计中确认），禁止沉淀 fail 现象、推测、partial 中间态、回归基线现状。

**产物**：
- `/AI_LabTest/report/{模块}-report-{ENV}-{YYYYMMDD}-{HHMMSS}.md`（即使全部通过也必须生成）
- `AI_LabTest/site-patterns/{domain}.md`「变更日志」节追加一段（如有新增/更新/作废事实）

---

## 全局执行铁律

1. **严格顺序**：1→2→3，禁止跳跃或调换
2. **门控强制**：步骤 1（用例设计）必须经用户确认方可进入步骤 2
2.1 **产物硬前置**：进入步骤 2 前必须校验步骤 1 测试用例存在且非空，缺失则退回步骤 1
3. **零源码修改**：仅可写 `/AI_LabTest/`；执行阶段只在被测系统页面内操作，绝不修改业务源码与配置
4. **来源可追溯**：每条执行结果 → 测试用例 ID → 覆盖维度 → oracle 来源（用户需求文档 / 用户提供用例 / 现状锁定）
5. **报告强制**：步骤 3 必须执行，无论结果如何
