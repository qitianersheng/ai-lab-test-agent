# 自动化测试工作流（3 步）

本文档定义了 AI_LabTest 的强制工作流。任何被加载到 Claude Code 的项目，只要复制本目录（`/AI_LabTest`）并按 `CLAUDE.md` 的指引引用规则，即可按本流程运行。

**铁律**：3 步必须严格按顺序执行。Step 1（用例设计）未通过用户门控时，不得进入 Step 2。

> **V0.14 变更**：术语统一——原「oracle」（测试预言）更名为「**预期依据**」，避免与 Oracle 数据库混淆；含义与判定规则不变。
> **V0.13 变更**：缺陷报告含 fail 时，Step 3 口头汇报**陈述式提示用户确认缺陷报告**、建议**如需修复新开对话窗口**（不用 AskUserQuestion；修代码绝不在 QA 会话内）。
> **V0.12 变更**：Step 3 **默认只产 2 份**——主报告（仅 概要 + 执行矩阵）+ 独立缺陷报告（仅未通过）；其余主报告章节与 历史归档 / latest / 多任务 / XLSX / DOCX 暂不默认生成。
> **V0.11 变更**：Step 2 需登录态时**先找** `AI_LabTest/.auth/{env}.{sanitize(key)}.storageState.json` 持久化登录态（**不是** environments.json）；无则登录（账号 / 浏览器手动登录）并把会话**存成 storageState 复用**，仍不行才判 blocked。见 `test-execution.md`「登录态建立」。
> **V0.10 变更**：用户上传测试用例时**以上传为准**——AI 只审核不改写、把不合适处列「审核提醒」交用户决定是否修改（不臆造 预期依据、不新增用例）。
> **V0.8 变更**：Step 3 新增**执行矩阵**（用例 12 列 + 执行 5 列，主报告内）与**独立缺陷报告**（仅未通过用例，fail 进正文 / partial·blocked 进附录），见 `test-report.md §2.8 / §2.9`。
> **V0.7 变更**：测试用例产物统一为**单个 Markdown 表格**（`{任务}-testcase.md`，12 列见 `test-case-completeness.md §1.1`）；预期依据 + 验证性质写入「需求引用」列；不再出 JSON / Excel。
> **V0.6 变更**：Step 1 输入来源由二选一增至三选一，新增「依据会话内容生成需求文档」（AI 回溯本轮对话提炼→落盘 `testCase/{任务}-requirement.md`→用户确认→逐格设计；预期依据逐条判定）。
> **V0.5 变更**：取消用户录入「模块名」。原「模块」作为全链路命名键与 `TC-` ID 前缀的角色，改由 **Step 1 自动生成的「任务名」**承担（语义优先、时间戳兜底）。本文档中 `{模块}` 占位符统一更名为 `{任务}`。
> **V0.4 变更**：剔除「代码库分析 / 需求分析 / 需求评审」三步。**测试用例设计**直接以用户提供的需求文档或用户直接给的测试用例为输入，不再做代码库扫描、三级回退需求发现、4 维度评审。流程由 6 步精简为 3 步。
> **V0.3 变更**：取消旧「测试脚本生成」步（不再生成 `.spec.ts`）。测试用例（Step 1 产物）直接交给 AI——AI 通过 Playwright MCP 浏览器工具**实时驱动浏览器**逐条执行用例、对照「预期结果」自判四态。

## 步骤 1 — 测试用例设计

**目标**：基于用户提供的输入设计测试用例，对照 `rules/test-case-completeness.md` 验证。

**输入来源（V0.6 · 用户驱动，三选一）**：

| 来源 | 处理 | 默认预期依据 |
|---|---|---|
| **用户提供需求文档**（路径 / 粘贴文本：PRD / 设计稿 / 接口契约等） | 为「需求 × 适用维度」逐格设计用例 | 功能验证（应然） |
| **依据会话内容生成需求文档**（AI 回溯本轮对话提炼成文） | 提炼→落盘 `{任务}-requirement.md`→用户确认→逐格设计用例 | 逐条判定：`[用户陈述]`/经确认升级 → 功能验证；`[AI推断]` → 回归基线 |
| **用户直接提供测试用例**（清单 / 表格 / 描述） | **以上传为准**：格式归整 + 审核 + 列「审核提醒」交用户裁定（不改写内容、不臆造 预期依据、不新增） | 沿用用户标注；未标则按 §1.6 判定 |

> 不再做代码库分析、三级回退需求发现、4 维度需求评审。若用户三者都没有，提示其先提供其一；**不**自行从代码反推需求。照抄当前 UI 现状、或会话内容实为代码反推得到的预期，只能标 `回归基线`（见 `test-case-completeness.md §1.6`）。

**任务名（自动生成，无需用户录入）**：本步据用户输入自动确定一个任务名 `{任务}`，作为本轮全链路命名键与 `TC-{任务}-{编号}` ID 前缀。**语义优先、时间戳兜底**：① 用户在参数里显式给名 → 清洗为文件名安全 slug 后采用；② 否则从需求 / 用例提炼核心主题生成简短语义 slug（如「用户登录」→ `登录`/`login`）；③ 主题难判定或同名文件已存在 → 追加 `-{YYYYMMDD}`（仍冲突再加 `-{HHMMSS}`）。生成后在用户门控里告知，用户可改名。

**操作**：

1. **先用 `AskUserQuestion` 让用户选择输入来源**：① 我有需求文档 → 随后**主动发起「导入需求文档」对话**，请用户拖拽 / ＋附件上传、`@` 引用项目内文件、粘贴内容或给路径（路径用 `Read` 读，PDF 多页用 `pages`），等真正给进来后再设计；② 依据会话内容生成需求文档 → AI **只回溯本轮对话**提炼成文、逐条标 `[用户陈述]`/`[AI推断]`、落盘 `{任务}-requirement.md`、**经用户确认**后再设计；③ 我没有需求文档 → 直接给测试用例（**以上传为准、AI 只审不改**：格式归整 + 审核出「审核提醒」交用户裁定，用户决定是否改，不改写内容、不臆造 预期依据）。三者都没有则提示先准备其一，**不**从代码反推。
2. 据用户输入按上文「任务名」规则确定本轮任务名 `{任务}`。
3. 为每个「需求 × 维度」组合生成测试用例条目（用户直接给用例时则**以上传为准、只审不改**：格式归整 + 审核出「审核提醒」交用户裁定，不改写内容、不臆造 预期依据）。
4. 每条用例 = Markdown 表格一行，含 **12 列**（顺序固定，详见 `test-case-completeness.md §1.1`）：

   | # | ID | 优先级 | 用例类型 | 模块 | 需求引用 | 用例标题 | 前置条件 | 测试操作 | 预期结果 | 断言 | 清理 |
   |---|----|------|--------|-----|--------|--------|--------|--------|--------|----|----|

   - 模块 = 本轮任务名 `{任务}`；用例类型取 §2.1 八类之一；断言填 L1–L4（§3.2）
   - **需求引用**列写 `<预期依据> · <验证性质>`（功能验证 / 回归基线，见 §1.6）—— 预期依据即落于此列

5. 对照完整性规则核验：结构 / 覆盖 / 断言 / 隔离 / **顺序** / **数据** / **权限**
6. 用例执行顺序按 `test-case-completeness.md §6` 排序（主流程 → 同页面 → 依赖前置 → 同账号 → 只读靠后）；CRUD 链路按序组织
7. 涉及数据创建的用例按 `test-case-completeness.md §7` 维护数据追踪（`auto-uitest-{时间戳}` 前缀 + 「先复用再最小构造」原则）
8. 多角色用例按 `test-case-completeness.md §8` 用隔离会话同路径比较，禁止根据角色名推断

**用户门控**：
- 将完整用例清单呈现给用户
- 缺口处置（添加 / 推迟 / 跳过）由用户确认
- 若本批用例**全部**为「回归基线」（预期依据 = 现状锁定），额外提示「这些用例只锁定现状、不验证正确性，是否补充权威需求来源（PRD / 产品确认）？」

**产物**：`/AI_LabTest/testCase/{任务}-testcase.md`（**单个 Markdown 表格**，12 列见 `test-case-completeness.md §1.1`；含数据追踪，如适用）。

## 步骤 2 — 测试执行（AI 实时驱动 Playwright）

**目标**：把已批准的测试用例**直接交给 AI 执行**——AI 通过 Playwright MCP 浏览器工具实时驱动浏览器逐条执行用例，对照「预期结果」自判四态，捕获证据。**严禁在执行阶段修改源代码**（详见 `rules/test-execution.md`）。

**入口硬校验**：`/AI_LabTest/testCase/{任务}-testcase.md` 存在且非空，否则退回步骤 1。

**操作**：

1. 完成环境预检（白名单仅 `local` + `SIT`；询问用户目标环境；探活被测地址；详见 `test-execution.md §0`）。
2. 选执行模式：**可见**（有头浏览器，操作肉眼可见）/ **后台**（无头，更快）。
3. Read `/AI_LabTest/testCase/{任务}-testcase.md`，逐条用例：用浏览器工具（navigate / click / type / fill_form / snapshot / wait_for / take_screenshot）满足前置条件（如登录；需登录态时**先找 `.auth/{env}.{sanitize(key)}.storageState.json` 持久化登录态**，无则登录并存盘复用，见 `test-execution.md`「登录态建立」）→ 执行测试操作 → 对照「预期结果」判定四态。
4. **四态自判**（详见 `test-execution.md §2`）：
   - `pass`：预期可观察结果完全出现
   - `fail`：预期明确未出现且可复现（疑似应用缺陷，保留事实、不放水）
   - `partial`：部分满足 / 用例被部分跳过
   - `blocked`：前置/路径/登录态无法建立、依赖或地址不可达——**不是应用 bug**
5. 每条用例截图留证；落盘逐条结果，归约为结构化 `run.json`（四态计数 + 逐条状态 + 证据路径）。

**产物**：`/AI_LabTest/report/{任务}-{ENV}.run.json`（结构化执行事实，供步骤 3 报告消费）+ 证据截图。

## 步骤 3 — 测试报告生成

**目标**：按 `rules/test-report.md` 生成结构化报告。

**报告必含章节**：
**主报告默认只含 2 节**：
- 概要（总数 / pass / fail / partial / blocked / 时间 + 通过率铁律）
- **执行矩阵**（用例 12 列 + 执行 5 列：实际结果 / 执行状态 / 证据 / 录像 / 失败·阻塞原因，与用例一一对应；见 `test-report.md §2.8`）

> 任务结果 / 失败明细 / 需求覆盖矩阵 / 覆盖缺口 / 应用 Bug 清单 / 测试侧后续动作 **暂不输出**（模板见 `test-report.md §2.2–§2.7`，按需再开）。

**另出独立缺陷报告**（`{任务}-缺陷报告-{ENV}-…md`，见 `test-report.md §2.9`）：仅未通过用例——fail 进缺陷正文、partial/blocked 进非应用缺陷附录。

**经验回写（Step 3 末尾强制）**：
报告生成完成后，按 `rules/test-report.md §10` 把本轮已验证事实增量写回 `AI_LabTest/site-patterns/{domain}.md` 的「变更日志」节。
仅沉淀已验证事实（来自功能验证 pass 用例 / blocked 已确认根因 / 用户在用例设计中确认），禁止沉淀 fail 现象、推测、partial 中间态、回归基线现状。

**产物**：
- `/AI_LabTest/report/{任务}-report-{ENV}-{YYYYMMDD}-{HHMMSS}.md`（主报告，含执行矩阵；即使全部通过也必须生成）
- `/AI_LabTest/report/{任务}-缺陷报告-{ENV}-{YYYYMMDD}-{HHMMSS}.md`（独立缺陷报告，仅未通过用例）
- `AI_LabTest/site-patterns/{domain}.md`「变更日志」节追加一段（如有新增/更新/作废事实）

## 全局执行铁律

1. **严格顺序**：1→2→3，禁止跳跃或调换
2. **门控强制**：步骤 1（用例设计）必须经用户确认方可进入步骤 2
2.1 **产物硬前置**：进入步骤 2 前必须校验步骤 1 测试用例存在且非空，缺失则退回步骤 1
3. **零源码修改**：仅可写 `/AI_LabTest/`；执行阶段只在被测系统页面内操作，绝不修改业务源码与配置
4. **来源可追溯**：每条执行结果 → 测试用例 ID → 覆盖维度 → 预期依据（用户需求文档 / 会话提炼需求 / 用户提供用例 / 现状锁定）
5. **报告强制**：步骤 3 必须执行，无论结果如何
