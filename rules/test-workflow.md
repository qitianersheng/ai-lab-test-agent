# 自动化测试工作流（6 步）

本文档定义了 AI_LabTest 的强制工作流。任何被加载到 Claude Code 的项目，只要复制本目录（`/AI_LabTest`）并按 `CLAUDE.md` 的指引引用规则，即可按本流程运行。

**铁律**：6 步必须严格按顺序执行。前一步未通过用户门控时，不得进入下一步。

> **V0.3 变更**：取消旧「测试脚本生成」步（不再生成 `.spec.ts`）。测试用例（Step 4 产物）直接交给 AI——AI 通过 Playwright MCP 浏览器工具**实时驱动浏览器**逐条执行用例、对照「预期结果」自判四态。流程由 7 步精简为 6 步。

---

## 流程总览

| 步骤 | 名称 | 用户门控 | 输出位置 |
|---|---|---|---|
| 1 | 代码库分析 | 是（确认测试范围） | `/AI_LabTest/analysis/codebase-overview.md` |
| 2 | 需求分析 | 是（确认需求清单） | `/AI_LabTest/requirements/{模块}-requirement.md` |
| 3 | 需求评审 | 是（缺口处置） | `/AI_LabTest/requirements/{模块}-review.json` + 更新需求文档 |
| 4 | 测试用例设计 | 是（确认用例） | `/AI_LabTest/testCase/{模块}-testcase.md` |
| 5 | 测试执行（AI 实时驱动 Playwright） | 否 | 结构化执行结果 `/AI_LabTest/report/{模块}-{ENV}.run.json` + 证据截图 |
| 6 | 测试报告 | 否 | `/AI_LabTest/report/{模块}-report-{ENV}-{YYYYMMDD}-{HHMMSS}.md` |

---

## 步骤 1 — 代码库分析

**目标**：建立对被测系统的结构性认知，确定本轮测试范围。

**操作**：
1. 按 `rules/codebase-analysis.md` 扫描代码库
2. 输出模块矩阵（模块名 / 路由 / 主要功能 / 数据依赖 / 鉴权要求）
3. 写入 `/AI_LabTest/analysis/codebase-overview.md`

**用户门控**：
- 呈现模块清单，询问用户：
  - 「本轮要测试哪些模块？」
  - 「是否有需要排除的模块？」
- 用户未确认前不得进入步骤 2

**产物**：`/AI_LabTest/analysis/codebase-overview.md` + 经用户确认的测试范围。

---

## 步骤 2 — 需求分析

**目标**：拿到可评审的需求清单。

**统一归一**：无论需求有无现成文档，唯一标准产物始终是 `{模块}-requirement.md`——有文档（用户提供或 `/docs` 等目录命中）则结构化写入并标 `PROJECT_DOC`，无文档则反推并标 `REVERSE_ENGINEERED`。下游步骤 3 永远只读这一个文件。

**预估耗时（区间 + 依赖说明）**：

进入本步骤时，先按命中的回退路径给用户一个**区间预估**，让用户知道大致等待时长。耗时主要取决于走到哪一级回退：

| 命中路径 | 预估区间 | 主要耗时来源 |
|---|---|---|
| L1 用户直接提供文档 | ~1 分钟 | 解析、结构化已有文档 |
| L2 项目内扫描 | 1–3 分钟 | 扫描候选目录 + 用户选择 + 解析 |
| L3 代码反推 | 3–8 分钟 | 读路由/表单/错误处理/DB 模型反推需求 |

呈现话术示例：「预计 1–5 分钟，取决于是否需要从代码反推需求（L3 最慢）。确定路径后会更新为更准确的预估。」
模块数量越多、源码越复杂，取区间上界。

**操作**（按 `rules/requirement-discovery.md` 的三级回退）：

1. **L1 用户提供**：询问用户是否有需求文档（路径或粘贴文本）
2. **L2 项目内扫描**：若用户无法提供，扫描以下位置（用户文档通常在 `/docs`，但不收敛到单一目录）：
   - `docs/`、`doc/`、`documentation/`
   - `requirements/`、`PRD/`、`specs/`、`.planning/`
   - 根目录 `*.md`（README 除外）
   - 对当前模块给候选文档算置信度（文件名精确 / 含模块名 / 正文命中），**唯一高置信命中直接采用**，多候选或中低置信才弹 `AskUserQuestion` 让用户选；选项**始终带上**「手动指定其他文件」与「该模块无文档→反推」
3. **L3 代码反推**：若前两级均无（或用户选「无文档」），**先确认「确实没有现成文档吗」再反推**需求（路由 / 表单 / 错误处理 / DB 模型），并明确标注 `REVERSE_ENGINEERED`

**用户门控**：
- 将每个模块的需求清单呈现给用户
- 每条需求必须标注来源：`USER` / `PROJECT_DOC` / `REVERSE_ENGINEERED`
- 用户确认后方可进入步骤 3

**产物**：`/AI_LabTest/requirements/{模块}-requirement.md`。

---

## 步骤 3 — 需求评审

**目标**：评审需求的可测试性与完整性，闭合所有逻辑缺口。

**入口硬校验（强制，先于一切操作）**：

需求评审消费的是步骤 2 的产物，没有需求清单就无法评审。进入步骤 3 前必须校验：

1. `/AI_LabTest/requirements/{模块}-requirement.md` **存在**
2. 且**非空**（含至少 1 条带来源标注的需求，而非仅有模板骨架）

校验失败 → **硬拦截**：禁止进入评审，明确告知用户「步骤 2 尚无有效输出，需先返回步骤 2 生成需求清单」，并退回步骤 2。不提供「知情后跳过」选项——评审无可评审对象时强行进入只会产生空评审。

> 注：UI 若把步骤 2 标为「可跳过」，指的是其**用户门控确认**可跳过，而非产物可缺失。步骤 2 产物始终是步骤 3 的硬前置。

**操作**（按 `rules/requirement-review.md` + `rules/requirement-completeness.md`）：

1. 对每个模块的需求按 4 维度评分：清晰度 / 完整度 / 可测试性 / 原子性（详见 `requirement-review.md`）
2. 对每个需求填写覆盖矩阵（详见 `requirement-completeness.md`）：

   ```
   | 路径类型   | 描述                  | 状态 |
   |-----------|----------------------|------|
   | 正常路径   | 预期操作产生预期结果   | ?    |
   | 空/无输入  | 空白字段或缺失参数     | ?    |
   | 无效输入   | 格式错误/超范围/非法字符 | ?    |
   | 边界值     | 最小/最大/超限          | ?    |
   | 错误反馈   | 失败时的可见错误消息    | ?    |
   | 状态恢复   | 出错后能重试/返回有效态  | ?    |
   ```

3. 如需求触及鉴权/数据生命周期，额外补充对应维度

**用户门控（强制交互）**：
- 评分 `< 80` 或存在 `MISSING` 维度：必须逐项与用户确认
  - 「当 [场景] 时应该发生什么？」
  - 「这个维度是补充测试 / 跳过 / 推迟到下次？」
- 评分 `< 60`：默认 `reject`，需用户决定是否退回修订
- 评分 `≥ 80` 且无 `MISSING`：可直接进入步骤 4

**产物**：
- `/AI_LabTest/requirements/{模块}-review.json`（评分快照）
- 更新后的 `/AI_LabTest/requirements/{模块}-requirement.md`（缺口已闭合）

---

## 步骤 4 — 测试用例设计

**目标**：基于已评审需求设计测试用例，对照 `rules/test-case-completeness.md` 验证。

**操作**：

1. 为每个「需求 × 维度」组合生成测试用例条目
2. 每个测试用例必须包含：

   | 字段 | 说明 | 必填 |
   |---|---|---|
   | ID | `TC-{模块}-{编号}` | 是 |
   | 模块 | 所属模块 | 是 |
   | 需求引用 | 覆盖的需求 ID + 维度 | 是 |
   | 目的 | 测试验证什么 | 是 |
   | 前置条件 | 操作前所需状态 | 是 |
   | 测试操作 | 具体用户操作 | 是 |
   | 预期结果 | 可观察的结果 | 是 |
   | 断言级别 | L1-可见 / L2-内容 / L3-状态 / L4-行为 | 是 |
   | 清理 | 状态重置 | 如需要 |

3. 对照完整性规则核验：结构 / 覆盖 / 断言 / 隔离 / **顺序** / **数据** / **权限**
4. `test()` 顺序按 `test-case-completeness.md §6` 排序（主流程 → 同页面 → 依赖前置 → 同账号 → 只读靠后）；CRUD 链路用 `test.describe.serial` 包裹
5. 涉及数据创建的用例按 `test-case-completeness.md §7` 维护数据台账（`auto-uitest-{时间戳}` 前缀 + 「先复用再最小构造」原则）
6. 多角色用例按 `test-case-completeness.md §8` 用隔离会话同路径比较，禁止根据角色名推断

**用户门控**：
- 将完整用例清单呈现给用户
- 缺口处置（添加 / 推迟 / 跳过）由用户确认

**产物**：`/AI_LabTest/testCase/{模块}-testcase.md`（含数据台账章节，如适用）。

---

## 步骤 5 — 测试执行（AI 实时驱动 Playwright）

**目标**：把已批准的测试用例**直接交给 AI 执行**——AI 通过 Playwright MCP 浏览器工具实时驱动浏览器逐条执行用例，对照「预期结果」自判四态，捕获证据。**严禁在执行阶段修改源代码**（详见 `rules/test-execution.md`）。

**入口硬校验**：`/AI_LabTest/testCase/{模块}-testcase.md` 存在且非空，否则退回步骤 4。

**操作**：

1. 完成环境预检（白名单仅 `local` + `SIT`；询问用户目标环境；探活被测地址；详见 `test-execution.md §0`）。
2. 选执行模式：**可见**（有头浏览器，操作肉眼可见）/ **后台**（无头，更快）。
3. Read `/AI_LabTest/testCase/{模块}-testcase.md`，逐条用例：用浏览器工具（navigate / click / type / fill_form / snapshot / wait_for / take_screenshot）满足前置条件（如登录）→ 执行测试操作 → 对照「预期结果」判定四态。
4. **四态自判**（详见 `test-execution.md §2`）：
   - `pass`：预期可观察结果完全出现
   - `fail`：预期明确未出现且可复现（疑似应用缺陷，保留事实、不放水）
   - `partial`：部分满足 / 用例被部分跳过
   - `blocked`：前置/路径/登录态无法建立、依赖或地址不可达——**不是应用 bug**
5. 每条用例截图留证；落盘逐条结果，归约为结构化 `run.json`（四态计数 + 逐条状态 + 证据路径）。

**产物**：`/AI_LabTest/report/{模块}-{ENV}.run.json`（结构化执行事实，供步骤 6 报告消费）+ 证据截图。

---

## 步骤 6 — 测试报告生成

**目标**：按 `rules/test-report.md` 生成结构化报告。

**报告必含章节**：
- 概要（总数 / pass / fail / partial / blocked / 时间）
- 模块结果
- 失败明细（应用 bug / 测试 bug / 环境问题 / 路径不可建立 / flaky）— 备注按三段式
- 需求覆盖矩阵
- 覆盖缺口
- 应用 Bug 清单（**仅事实通报**：ID / 严重 / 模块 / 用例 / 描述 / 状态）
- 测试侧后续动作（补用例 / 调整执行 / 重跑 / 推迟覆盖）— **禁含** bug 修复方案、修复优先级、发布与否

**经验回写（Step 6 末尾强制）**：
报告生成完成后，按 `rules/test-report.md §10` 把本轮已验证事实增量写回 `AI_LabTest/site-patterns/{domain}.md` 的「变更日志」节。
仅沉淀已验证事实（来自 pass 用例 / blocked 已确认根因 / 用户评审确认），禁止沉淀 fail 现象、推测、partial 中间态。

**产物**：
- `/AI_LabTest/report/{模块}-report-{ENV}-{YYYYMMDD}-{HHMMSS}.md`（即使全部通过也必须生成）
- `AI_LabTest/site-patterns/{domain}.md`「变更日志」节追加一段（如有新增/更新/作废事实）

---

## 全局执行铁律

1. **严格顺序**：1→2→3→4→5→6，禁止跳跃或调换
2. **门控强制**：步骤 1、2、3、4 必须经用户确认方可进入下一步
2.1 **产物硬前置**：进入步骤 3 前必须校验步骤 2 产物存在且非空，缺失则硬拦截退回步骤 2（详见步骤 3「入口硬校验」）；进入步骤 5 前必须校验步骤 4 测试用例存在且非空
3. **零源码修改**：仅可写 `/AI_LabTest/`；执行阶段只在被测系统页面内操作，绝不修改业务源码与配置
4. **缺口必交互**：步骤 3 中所有 `MISSING` 或低分维度必须与用户对话确认
5. **来源可追溯**：每条执行结果 → 测试用例 ID → 需求维度 → 需求来源（USER/PROJECT_DOC/REVERSE_ENGINEERED）
6. **报告强制**：步骤 6 必须执行，无论结果如何
