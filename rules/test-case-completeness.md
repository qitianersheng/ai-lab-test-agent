# 测试用例完整性检查

## 1. 结构完整性

每个测试用例必须包含以下结构元素。缺少任何元素将使测试用例不完整。

### 1.1 必填元素

| 元素 | 描述 | 示例 |
|---|---|---|
| **用例标题** | 测试验证什么 — 一个清晰、具体的目标（即测试目的，作为用例标题） | "验证空字段显示验证错误" |
| **优先级** | 该用例的风险/重要性分级 P0/P1/P2/P3（见 §1.4） | P1 |
| **用例类型** | 该用例所属的覆盖维度，取 §2.1 的八类之一 | 边界值 / 用户体验 |
| **前置条件** | 测试操作开始前所需的状态 | 已登录、在 /login 页面、无缓存的认证 |
| **测试操作** | 执行的具体用户操作，**按步骤拆分**（与「预期结果」逐步 1:1，见 §1.5） | 步骤1：填写空账号；步骤2：点击登录 |
| **预期结果** | 每个操作步骤后必须可观察到的结果，**每步一条、以【检查点类别】开头**（见 §1.5） | 【UI检查】出现「请输入账号和密码」提示 |
| **预期结果来源（oracle）** | 预期结果的依据来自哪里 —— 决定本用例能否判对错，详见 §1.6 | PRD / 设计稿 / API契约 / 产品确认 / 现状锁定 |
| **清理** | 重置状态以避免污染后续测试 | localStorage.removeItem、注销 |

### 1.2 结构模板

```typescript
// oracle 来源: PRD#REQ-login-001（应然）→ 验证性质: 功能验证   ← 见 §1.6
test('[目的]', async ({ page }) => {
  // 前置条件（在 beforeEach 中或内联）
  await page.goto('/login');

  // 测试操作
  await page.getByPlaceholder('请输入账号').fill('');

  // 预期结果
  await expect(page.getByText('请输入账号和密码')).toBeVisible();

  // 清理（在 afterEach 中或内联）
});
```

### 1.3 缺失元素严重程度

| 缺失元素 | 严重程度 | 影响 |
|---|---|---|
| 测试目的 | 严重 | 无法确定测试验证什么 |
| 前置条件 | 严重 | 测试行为在不同运行中不可预测 |
| 预期结果 | 严重 | 无论实际行为如何测试都会通过 |
| 预期结果来源（oracle） | 严重 | 不知道预期结果是「应然」还是「现状」，无法判断用例在验证对错还是仅锁定现状 |
| 测试操作 | 严重 | 测试没有有意义的操作 |
| 优先级 | 中 | 无法做风险排序与执行优先级编排 |
| 清理 | 高 | 状态污染影响其他测试 |

### 1.4 优先级定义（P0–P3）

按风险与重要性给每条用例分级。分布比例为**参考指引**（按项目实际浮动，不强套；但**不应整批集中在某一级**）：

| 级别 | 含义 | 参考占比 |
|---|---|---|
| **P0** | 核心功能，失败即版本打回（主流程必经） | ~10% |
| **P1** | 基本功能 + 重要错误/边界 | ~20% |
| **P2** | 异常/中断/容错/UI，其中约 15% 为用户体验用例 | ~55% |
| **P3** | 性能/兼容/安全/可用性 | ~15% |

### 1.5 测试步骤：操作↔预期 1:1 + 检查点分类

- 用例的「测试操作」由**有序步骤**组成，每步含「操作内容」+「该步的预期结果」，**严格 1:1**：禁止一个操作对应多条预期，也禁止多个操作合并到一条预期。
- 每条**预期结果以【检查点类别】开头**，多个检查点用逗号分隔、不换行。类别仅用以下 **6 类**（UI 自动化适用子集）：
  **【UI检查】【业务功能检查】【数据检查】【通知检查】【异常检查】【权限检查】**
- 预期要**具体、可验证、有源码依据**（真实文案/元素/路由/状态），禁止「体验良好」「有间距」这类无法稳定断言的泛词；拿不准标「待真机确认」。

示例（单条用例的步骤，操作与预期逐步对应）：

| 步骤 | 操作内容 | 预期结果 |
|---|---|---|
| 1 | 在 /login 不输入账号密码，点击「登录」 | 【UI检查】字段下方出现「请输入账号和密码」红色提示 |
| 2 | 输入有效账号 + 错误密码，点击「登录」 | 【业务功能检查】Toast 显示「账号或密码错误」，【UI检查】仍停留在 /login |

### 1.6 预期结果来源（oracle）与验证性质

「预期结果」必须能追溯到一个来源（oracle）。**来源的性质决定这个用例能否用来判断「对错」**，因此每个用例除 §1.1 的「用例类型」（§2.1 八类覆盖维度）外，还必须显式标注 `oracle 来源` 与由它推导出的 `验证性质`。

> 两根轴不要混：**用例类型**=覆盖维度（边界值/状态转换/业务规则…，见 §2.1）；**验证性质**=这条用例在「验对错」还是「锁现状」（功能验证/回归基线，本节）。

**铁律**：预期结果若来自被测代码本身（代码反推 / 照抄当前 UI 现状），oracle 与被测对象同源 —— 用例只是在复述代码现状，会永远 pass，发现不了任何「代码与意图不符」的缺陷。这类用例只能当回归基线，**禁止**当功能验证。

**两类 oracle → 两种验证性质**

| oracle 来源 | 性质 | 验证性质 | 作用 | 红线 |
|---|---|---|---|---|
| `PRD` / `设计稿` / `API契约` / `产品确认` | 应然（权威） | **功能验证** | 判断代码行为对错，抓「代码 ≠ 意图」的缺陷 | — |
| `现状锁定`（代码反推 / 当前 UI 观察） | 实然（现状） | **回归基线** | 锁定当前行为、防未来回归 | 报告中**不得**表述为「功能正确 / 验证通过」，只能说「现状已锁定，无回归」 |

**与 Step 2 需求来源的映射**（承接 `requirement-discovery.md` 的 `来源:` 标注）

| 需求来源（Step 2） | 默认 oracle | 默认验证性质 | 升级为功能验证的条件 |
|---|---|---|---|
| `USER` / `PROJECT_DOC` | 应然 | 功能验证 | — |
| `REVERSE_ENGINEERED`（未确认） | 现状锁定 | 回归基线 | 仅当用户 / 产品对「应然行为」显式确认、并记入需求文档「评审补充」后，方可升级 |

**标注与门控约束**

- 每个用例**必须**标注：`oracle 来源: {PRD / 设计稿 / API契约 / 产品确认 / 现状锁定}` + `验证性质: {功能验证 / 回归基线}`。
- 缺 `oracle 来源` → 按 §1.3 记「严重」缺口。
- 若某模块用例**全部**为 `回归基线`，Step 4 用户门控必须显式提示「本模块用例仅锁定现状、不验证正确性，是否补充权威需求来源（PRD / 产品确认）？」，由用户裁定。

## 2. 覆盖完整性

模块的测试用例必须共同覆盖所有面向用户的行为。使用以下清单进行验证。

### 2.0 矩阵驱动、逐格生成（让条数由需求决定、可复现，不漏需求）

设计用例**不要凭感觉决定多少条**，而是**先建矩阵、再逐格生成**：

1. 对**每一条需求**，从 §2.1 的覆盖类型（八类维度）中判定**哪些适用**（按需求真实语义判「适用/不适用」——只读列表类可能不涉及权限/状态转换，不必硬凑八类）。
2. 得到 `需求 × 适用维度` 的格子清单后，**每个格子恰好 1 条用例**（仅当该格确有多个相互独立场景时至多 2 条，并在用例标题区分）。
3. **每条需求至少 1 条用例，一条都不能漏**；总条数应≈Σ(各需求的适用维度数)。

这样同一份需求重跑时，矩阵稳定 → 条数稳定在窄带、覆盖可复现（避免「同模块每次条数忽多忽少」）。生成后应有一道**确定性完整性校验**：逐条需求是否被覆盖、字段是否齐全、条数是否异常偏低；有缺口即补齐。

### 2.1 功能覆盖类型

| 覆盖类型 | 描述 | 最低要求 |
|---|---|---|
| **正向验证** | 核心用户流程成功完成 | 每个核心功能至少 1 个测试 |
| **异常场景** | 无效输入和错误场景 | 每个输入字段按等价类划分，**每个无效等价类各 1 个不同值**（空 / 超长 / 非法字符 / 错误格式 / 前后空格 / 注入样式…）；UI 显示的每条错误消息至少 1 个测试 |
| **边界值** | 边缘值（最小/最大/空/溢出） | 每个输入字段覆盖 `min-1 / min / max / max+1` 等边界点，**每点 1 个不同值**，禁止只测一个 |
| **状态转换** | 状态之间的转换（登录→已认证，空→有数据），含状态机的合法与非法迁移 | 每个可见状态变化至少 1 个测试；命中状态机时**状态迁移矩阵全覆盖**：合法迁移各 1 + **非法迁移各 1（验证被拒、状态不变）** |
| **权限边界** | 角色之间的访问控制 | 每个受限功能每个角色至少 1 个测试 |
| **业务规则** | 需求中的业务约束/计算/状态机规则，含多个独立条件共同决定同一结果的判定表 | 每条显式业务规则至少 1 个测试；**多条件决定同一结果时产出判定表**，每条规则 ≥1 用例，组合爆炸按 pairwise 压缩 + 关键组合（金额/权限/不可逆/安全）强制保留 |
| **数据一致性** | 同一数据在不同视图/接口/刷新后保持一致 | 涉及增删改的数据至少 1 个一致性测试 |
| **用户体验** | 可自动化的体验关注点（见 §2.4） | 每个核心交互至少覆盖 1 个可自动化 UX 点 |

**判定表 / 状态迁移用例实现要点**（融入「业务规则」「状态转换」两类，不另立维度）：

- 判定表：一条规则一条用例（文档条目），参数化罗列、避免手抄/漏抄；组合爆炸时 pairwise 压缩，并在「完整性检查」中说明丢弃了哪些组合
- 状态迁移：合法迁移走正常断言；非法迁移断言「操作被拒 + 状态不变」
- 非法迁移中「纯防御性」那批（重复操作、终态→任意操作）标 `验证性质: 回归基线`（oracle = 现状锁定，见 §1.6），不计入功能验证通过率

### 2.2 UI 元素覆盖

对于每个页面，验证测试用例覆盖了：

- [ ] 所有输入字段（填写 + 验证）
- [ ] 所有按钮（点击 + 验证操作）
- [ ] 所有导航链接（点击 + 验证目标页面）
- [ ] UI 可以显示的所有错误消息
- [ ] 所有加载/空/成功状态
- [ ] 所有弹窗对话框（打开 + 交互 + 关闭）

### 2.3 覆盖缺口检测

对于给定模块，比较：

```
现有测试用例列表：
  - 测试 A：覆盖 [正常路径, 空输入]
  - 测试 B：覆盖 [无效输入]
  ...

所需覆盖（来自 requirement-completeness.md 矩阵）：
  - 正常路径     → 由测试 A 覆盖
  - 空输入    → 由测试 A 覆盖
  - 无效输入  → 由测试 B 覆盖
  - 边界       → 缺失
  - 错误反馈 → 缺失
  - 状态恢复 → 缺失
```

任何 **缺失** 行即为覆盖缺口。

### 2.4 用户体验维度（只收可自动化部分）

用户体验从六面拆解，**仅生成能在 Playwright 中稳定断言的部分**；美观/情感等不可自动化的主观项标「待人工复核」，不臆造断言。

| 维度 | 可自动化关注点（举例） |
|---|---|
| 功能体验 | 核心路径步骤数、是否有阻断、关键入口可达 |
| 易用性 | 高频操作是否触手可及、默认值/历史记录/一键清空是否存在 |
| 性能体验 | 关键操作响应是否 ≤ 约定阈值、加载态是否按预期出现/消失 |
| 视觉体验 | 关键文案/标签/布局结构是否符合规范（结构性，非主观美观） |
| 情感体验 | 空状态/成功反馈/偏好记忆是否存在（存在性可测） |
| 容错与异常体验 | 破坏性操作是否有二次确认、撤销/返回是否存在、异常提示是否清晰无技术黑话 |

**写法**：从**用户认知与情绪**角度写预期，如「用户立即明白操作成功，无需二次确认」「文案清晰无歧义、操作无停顿」「等待超过 2 秒，用户可能焦躁并重复点击」；**禁止**写「体验良好」这类泛词，每条 UX 预期指向单一关注点。

## 3. 断言完整性

每个测试操作必须至少有一个断言。无断言的操作是无意义的。

### 3.1 断言规则

| 规则 | 描述 |
|---|---|
| **禁止裸操作** | 每个 `click`、`fill`、`navigate` 后必须至少跟一个 `expect` |
| **断言结果而非操作** | 验证结果（用户看到的），而非操作本身 |
| **一个操作，一条断言链** | 单个用户操作可以有多个断言，但每个必须验证不同的可观察结果 |
| **异步断言优先** | 使用 web-first 断言（`toBeVisible`、`toHaveText`）先于检查内部状态 |

### 3.2 断言深度级别

| 级别 | 描述 | 使用场景 |
|---|---|---|
| **L1 - 可见性** | 元素出现在屏幕上 | 每个测试的基线 |
| **L2 - 内容** | 元素显示正确的文本/值 | 当显示的数据很重要时 |
| **L3 - 状态** | 页面 URL、localStorage 或 DOM 状态变化 | 当导航或数据持久化很重要时 |
| **L4 - 行为** | 元素被禁用、隐藏或交互状态变化 | 当 UI 响应加载/错误条件时 |

最低要求：每个测试必须达到 **L1**。关键流程应达到 **L2** 或 **L3**。

### 3.3 断言缺口示例

```typescript
// 不好 — 裸操作，无断言
await page.getByRole('button', { name: '登录' }).click();

// 不好 — 断言操作而非结果
await expect(page.getByRole('button', { name: '登录' })).toBeEnabled();

// 好 — 断言可观察的结果
await page.getByRole('button', { name: '登录' }).click();
await expect(page.getByText('账号或密码错误')).toBeVisible();       // L2
await expect(page).toHaveURL('/login');                             // L3
```

## 4. 隔离完整性

每个测试必须是独立的。一个测试的失败或状态变化不得影响另一个测试。

### 4.1 隔离规则

| 规则 | 描述 |
|---|---|
| **无测试顺序依赖** | 任何测试单独运行或以任何顺序运行都必须通过 |
| **在 beforeEach 中重置状态** | 每次测试前清除 cookies、localStorage、sessionStorage |
| **不共享可变状态** | 不要在测试之间共享会改变状态的变量 |
| **API 模拟隔离** | 路由模拟必须按测试设置，除非是只读的否则不应全局共享 |

### 4.2 常见隔离失败

| 失败模式 | 症状 | 修复 |
|---|---|---|
| 认证状态泄漏 | 顺序运行通过但单独运行失败 | 在 beforeEach 中添加 localStorage 清理 |
| API 模拟渗透 | 测试 A 的模拟影响测试 B | 在每个测试内定义路由模拟，而非在 beforeEach 中（除非所有测试需要相同模拟） |
| 导航陷阱 | 上一个测试将页面留在错误 URL | 在 beforeEach 中始终导航到目标页面 |
| 数据依赖 | 测试创建的数据被下一个测试读取 | 使用模拟数据或在 afterEach 中重置 |

## 5. 完整性检查流程

在执行模块测试之前，执行以下步骤：

### 步骤 1：结构检查
- 审查每个测试用例的 6 个必填元素（目的、前置条件、操作、结果、预期结果来源(oracle)、清理）
- 标记任何严重缺失元素

### 步骤 2：覆盖检查
- 列出页面上的所有 UI 元素和用户操作
- 将每个映射到现有测试用例
- 命中判定表 / 状态机的需求：核对判定表每条规则、状态迁移矩阵每个格（含非法迁移）是否都映射到用例
- 识别缺失覆盖项

### 步骤 3：断言检查
- 验证每个操作至少有 L1 级断言
- 标记裸操作（无断言的操作）

### 步骤 4：隔离检查
- 验证 beforeEach 正确重置状态
- 验证不存在测试顺序依赖
- 单独运行一个测试以确认独立性

### 步骤 5：报告
呈现摘要：

```
模块：[名称]
结构缺口：[数量] 严重，[数量] 高
覆盖缺口：[未覆盖项列表]
断言缺口：[裸操作列表]
隔离风险：[依赖列表]

建议操作：[添加测试 / 修复断言 / 添加清理]
```

### 步骤 6：生成后自查（发现问题直接修正到输出，不要把问题留给下游）

- **步骤顺序**是否合理（前置在前、有依赖的步骤有序）
- **操作↔预期是否 1:1** 且有因果关系（每个操作都有且仅有一条对应预期）
- **预期格式**：每条预期是否以【检查点类别】开头、是否具体可验证（无「体验良好」类泛词）
- **优先级**分配是否合理（核心主流程为 P0/P1，未整批集中在 P2；分布大致贴近 §1.4 参考占比）
- **命名与用词**：用例名是否清晰简洁、与目的一致；同一元素/动作上下文用词是否统一
- **维度覆盖**：是否覆盖了 §2.1 的八类维度（含业务规则/数据一致性/用户体验），有无明显缺口

## 6. 用例执行顺序原则

Step 4 设计用例 + Step 5 执行用例时，用例的执行顺序按以下优先级（高 → 低）排列（执行阶段 AI 按此顺序逐条驱动）：

1. **主流程优先**：创建 → 查看 → 编辑 → 删除，后续用例复用主流程产出的数据
2. **同页面连续**：同一页面/模块的用例排在一起，避免反复跳转页面
3. **依赖前置**：用例 B 依赖用例 A 的数据或状态时，A 排在 B 前面
4. **同账号连续**：同账号的所有用例连排，避免反复切换登录态
5. **只读靠后**：查询/列表/详情等只读验证排在写操作之后

### 6.1 实现方式

| 场景 | 实现 |
|---|---|
| 用例彼此独立（默认） | 用 `test.describe('{模块}', ...)` 包一组，Playwright 默认并行（5 workers） |
| 用例必须按序执行（CRUD 链路） | 用 `test.describe.serial('{CRUD 链}', ...)`，组内顺序 = 文件中 `test()` 声明顺序 |
| 跨模块依赖 | 拆到不同 spec 文件 + 用 `globalSetup` 准备共享前置数据；**不在测试中跨 spec 引用** |

### 6.2 顺序设计示例

```typescript
test.describe.serial('record CRUD 链路', () => {
  test('TC-record-001: 新增一条记录', async ({ page }) => { ... });   // 创建
  test('TC-record-002: 列表显示新增项', async ({ page }) => { ... }); // 查（复用 001）
  test('TC-record-003: 编辑该记录', async ({ page }) => { ... });     // 改（复用 001）
  test('TC-record-004: 删除该记录', async ({ page }) => { ... });     // 删（兜底清理）
});
```

### 6.3 反模式

- ❌ 把「先登录再查询」拆到两个独立 `test()` 并并行运行（查询会因未登录而 401）
- ❌ 在 `beforeAll` 创建数据但用 `test()` 默认并行删除（删除可能先于编辑跑）
- ❌ 用 sleep / hardcoded 等待替代顺序保证

## 7. 数据策略与数据追踪

### 7.0 两类测试数据，策略相反（先分清用途）

下面 §7.1 的「复用优先」只适用于**流程 / 实体数据**。**输入校验数据反着来 —— 主动多样化、不复用**。两者混用，就会出现「表单永远只填那几个值」。

| 数据用途 | 例 | 策略 |
|---|---|---|
| **流程 / 实体数据**（让用例有前置状态） | 一条待编辑的记录、一个待删的用户 | **复用 + 最小构造**（§7.1），防污染防爆炸 |
| **输入校验数据**（验证字段校验 / 边界 / 格式） | 用户名长度、金额范围、日期、特殊字符 | **主动多样化**：每个等价类 + 每个边界点用**不同的新值**，**禁止复用** |

**输入数据多样性（强制 —— 针对 §2.1 的异常 / 边界 / 业务规则判定表维度）**：

- 对每个输入字段先做**等价类划分 + 边界点**，每类 / 每点取**不同的代表值**
- **禁止**所有校验用例都填同一个「万能值」（如全用 `test123` / `1`）—— 那只覆盖一个等价类
- 边界用真实边界：`min-1 / min / max / max+1`；特殊输入覆盖：空 / 超长 / 前后空格 / 特殊字符 / 注入样式 / Unicode·emoji / 错误格式
- 这类输入数据是**一次性**的：**不纳入 §7.2 内联追踪、不要求复用**（目的是触发校验，不是建业务状态）

### 7.1 数据策略：先复用，再最小构造（仅限流程 / 实体数据）

判 `blocked` 之前，**必须先穷举**这些复用渠道：

1. 相邻或更早的测试用例已建立的数据
2. 现有列表记录、详情记录
3. 下拉选项、自动补全建议、校验提示给出的默认/枚举值
4. 已关闭用例（pass）创建出的数据
5. 已批准的上传文件或可复用附件

只有以上全部失败，才能构造新数据。构造原则：

- 只创建满足当前用例所需的**最小记录**
- 使用稳定可追溯的前缀：**`auto-uitest-{YYYYMMDD-HHMMSS}-{seq}`**
- 相邻用例间能复用就复用，不重复造
- 默认 `save`，**非用例明确要求或用户批准，不要 `submit`**（避免触发不可逆动作）
- **非用例明确要求，不删除/不覆盖已有业务数据**
- 不可逆动作（删除、提交审批、发送邮件）只在最小范围内执行

### 7.2 数据创建的追踪（轻量，不再单独成表）

> 变更：测试用例交付物为**单页 Excel**，不再额外维护「数据台账」sheet/章节。数据复用与清理通过下述约定**就近内联**到用例本身。

涉及数据创建的用例，按以下方式追踪，无需独立台账：

- 造数据用稳定可追溯前缀 **`auto-uitest-{YYYYMMDD-HHMMSS}-{seq}`**，写进该用例的「测试操作」步骤里
- 后续用例复用前序用例造出的数据时，在「前置条件」写明依赖（如「复用 TC-record-001 创建的 auto-uitest-…」）
- 需要回收的数据，在该用例「清理」字段写明（如「删除 auto-uitest-… 复位」）；CRUD 链路的删除用例兜底清理
- 执行阶段的真实数据生命周期由 Step 5 执行记录与 Step 6 报告承载，不在用例设计阶段维护静态台账

### 7.3 何时才算真的 blocked

只有以下条件**全部**满足时才能判 `blocked`：

- 没有任何可达的 UI 状态能暴露所需数据
- 没有相邻用例能建立该前置状态
- 无法安全构造所需的测试数据
- 缺失状态依赖于不可用的外部系统/权限/环境

## 8. 权限边界验证策略

涉及多角色的模块（当前项目：**user-management** 与 **practice-library**，admin-only）的用例设计必须遵守：

### 8.1 核心规则

通过**隔离会话下的同路径比较**来验证权限，**禁止**根据角色名称或主观假设推断权限行为。

### 8.2 会话隔离

- 每个账号使用独立的 `browser.newContext()` 或独立的 `storageState`
- 同一比较路径中账号归属保持稳定，**禁止**在共享浏览器状态中反复覆盖账号
- 推荐：用 `test.use({ storageState: 'auth/admin.json' })` 与 `auth/user.json` 隔离

### 8.3 比较内容

在两个账号之间，相同筛选条件 + 相同关键字 + 相同操作步骤下，对比：

| 维度 | 例 |
|---|---|
| 菜单可见性 / 入口 | 「用户管理」菜单 admin 可见 / user 隐藏 |
| 操作按钮 | `add` / `approve` / `submit` / `export` / `delete` 是否可见可点 |
| 列表数量与范围 | 同筛选下 admin 返回 N 条 / user 返回 M 条 |
| 下拉/自动补全可选范围 | 角色字段 admin 可选 admin+user / user 只能选自己 |
| 默认字段值 / 可编辑字段 | admin 可改 role / user 不能 |
| 导出内容范围 | admin 导出全部 / user 导出自己的 |

### 8.4 备注模板（接 §2.3 三段式）

> 1. **做了什么**：在相同筛选条件下，账号 admin 与账号 user 各自访问 `/user-management`
> 2. **看到了什么**：admin 看到 3 条记录 + 「新增/编辑/删除」按钮；user 直接被 401 重定向到 `/login`
> 3. **为什么足以关闭为 pass**：权限边界与需求 REQ-user-002 一致 → pass

### 8.5 不要过度归因到权限

- 用例本身不要求得出权限结论时，先按可见 UI 行为关闭用例
- 所有账号都出现同样的错误行为 → 更可能是产品缺陷（fail），不是权限差异
- 真实问题是缺数据 / 缺入口 / 导航错误时，**直接记录事实**，不要写成笼统的「权限问题」

### 8.6 何时判 blocked

仅以下场景才能因权限问题判 blocked：

- 必需的对比账号不可用（如 user 角色种子账号不存在）
- 必需会话无法建立
- 所有可用账号都无法访问该页面
- 所需权限状态依赖于无法安全模拟的后端变更（如数据库直改 ENUM）
