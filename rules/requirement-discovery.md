# 需求发现规范（步骤 2 · 需求分析）

**目标**：尽可能拿到完整、可评审的需求清单。采用三级回退策略，确保即便项目没有需求文档也能进入后续流程。

---

## 0. 核心原则：统一归一

**无论需求来自哪一级回退，步骤 2 的唯一标准产物始终是 `/AI_LabTest/requirements/{模块}-requirement.md`。**

- 模块**有文档**（用户提供或 `/docs` 等目录命中）→ 把文档内容**结构化写入**该文件，每条标 `PROJECT_DOC: {源文件路径}`，不直接引用原始文件。
- 模块**无文档** → 从代码反推生成该文件，每条标 `REVERSE_ENGINEERED`。

这样下游步骤 3（需求评审）**永远只读 `{模块}-requirement.md` 一个文件**，不需要判断"读 /docs 原文还是读生成产物"，全流程统一。源文件路径保留在来源标注里，保证可追溯。

---

## 0.1 模块 ↔ 需求文档关联表（复用记录）

为避免每次重复挑选文档，步骤 2 维护一份**关联注册表**：`AI_LabTest/requirements/_module-doc-map.json`。

```json
{
  "version": 1,
  "modules": {
    "登录": { "docs": ["docs/PRD-login.md"], "source": "USER_PROJECT", "updatedAt": "2026-06-02" }
  }
}
```

- `docs`：与该模块关联的需求文档（**项目内相对路径**）；`source`：`USER_PROJECT`（项目内选取）/ `USER_UPLOAD`（上传到 `docs/`）/ `NONE`（明确无文档，走反推）；`updatedAt`：最近更新日期。
- **进入 L1 前先查此表**：当前模块已有记录且文档仍存在 → 让用户选择「复用 / 重新选择 / 追加」，复用则直接读这些文档、**短路跳过 L2/L3**；文档已失效则剔除后重选。
- 用户为模块**选定或上传**需求文档后，把映射**合并写回**此表（不覆盖其他模块），供下次复用。

> 交互机制由各平台实现：CLI（Claude Code）用 `AskUserQuestion` 询问；桌面应用用选择/上传弹窗。本规范只约定**行为与产物**：用户已指定文档 → 仅依据这些文档结构化归一（标 `PROJECT_DOC`）、**不扫描其他文档、不代码反推**；未指定 → 走下方三级回退。

---

## 1. 三级回退策略

### L1 用户提供（最高优先级）

**询问用户**（必须主动问）：

> 是否有现成的需求文档？
> - 路径形式：请提供文件路径（支持 .md / .txt / .pdf / .docx）
> - 粘贴形式：请直接粘贴需求文本
> - 都没有：回答「无」，将自动进入 L2

**处理**：
- 路径：使用 Read 工具读取文件
- 粘贴：直接采用用户输入文本
- 多个文档：合并并按模块拆分

每条需求标注 `来源: USER`。

---

### L2 项目内扫描

**触发条件**：用户回答「无」或提供文档不完整。

> 约定：用户已有的需求文档**通常放在 `/docs`**，但**不收敛到单一目录**——仍扫描下表全部位置，避免漏掉散落文档。

**扫描位置**（按优先级）：

| 优先级 | 位置 | 说明 |
|--------|------|------|
| 1 | `docs/`、`doc/`、`documentation/` | 标准文档目录（用户放需求文档的约定位置） |
| 2 | `requirements/`、`PRD/`、`specs/` | 需求专用目录 |
| 3 | `.planning/`、`planning/` | GSD 等规划工具目录 |
| 4 | 根目录 `*.md`（README 除外） | 散落文档 |
| 5 | `README.md` | 兜底（功能描述部分） |

**处理：自动匹配 → 仅歧义时确认 → 统一归一**

对**当前模块**，按下表给每个候选文档算置信度（模块名/别名/路由来自步骤 1 的模块矩阵）：

| 置信度 | 判据 |
|--------|------|
| 高 | 文件名精确命中：`{模块}.md` / `{模块别名}.md` |
| 中 | 文件名或文档标题**包含**模块名/别名 |
| 低 | 正文关键词命中该模块的路由/功能 |

按置信度决定是否打扰用户：

1. **唯一高置信命中** → **直接采用**，不弹问，仅提示「已采用 `{file}` 作为 {模块} 需求来源，如需更换请告知」（保留纠错口）
2. **多候选 / 仅有中低置信 / 零命中** → 用 `AskUserQuestion` 让用户单选，选项构成：
   - 各候选文档（按置信度排序，每项附**来源路径** + 置信度标签 + 必要时正文首段预览）
   - **`手动指定其他文件`**（用户给路径或粘贴）—— **始终带上**
   - **`该模块无文档 → 走代码反推`** —— **始终带上**
3. 用户选定文档后 → 按 §0 **结构化写入** `{模块}-requirement.md`，每条标 `来源: PROJECT_DOC: {file_path}`
4. 用户选「无文档」→ 进入 L3（按 L3 的「先问再反推」二次确认）

> 「手动指定」与「无文档→反推」两个兜底选项**任何情况下都出现**，保证用户永远有退路，不被自动匹配绑架。

---

### L3 代码反推（兜底）

**触发条件**：L1、L2 均无产出，或与 L1/L2 联合补全缺失模块。

**先问再反推（强制）**：在动手反推前，必须先向用户确认「{模块} 确实没有现成需求文档吗？」——避免用户手里有文档只是还没放进项目/`/docs`。用户确认「确实没有」后才反推。

**反推策略**：

| 代码信号 | 推导出的需求维度 |
|---------|----------------|
| 路由表 | 功能模块 + 入口 |
| 表单字段 + validators | 输入项 + 校验规则 |
| 按钮 onClick / submit | 用户操作 |
| 错误处理 / try-catch | 异常路径 |
| Loading / Empty 状态 | 状态生命周期 |
| 角色判断 / 权限中间件 | 权限边界 |
| DB schema 字段约束 | 数据约束（必填、唯一、最大长度） |
| API 响应码 | 成功/失败分支 |

**输出**：
- 草拟需求，**每条标注 `来源: REVERSE_ENGINEERED`**
- 列出推导依据（代码位置：`file:line`）
- 明确告知用户「以下需求由代码反推，可能不完整或与产品意图不符，请逐条确认」

---

## 2. 输出格式

每个模块写入 `/AI_LabTest/requirements/{模块}-requirement.md`：

```markdown
# 需求文档 — {模块名}

**生成时间**：YYYY-MM-DD
**主要来源**：USER / PROJECT_DOC / REVERSE_ENGINEERED / MIXED

---

## REQ-{模块}-001：{需求标题}

**来源**：USER | PROJECT_DOC: docs/PRD.md#L10 | REVERSE_ENGINEERED: src/pages/Login.tsx:42
**优先级**：P0 / P1 / P2

### 描述
{用户故事或一句话描述}

### 前置条件
- ...

### 验收条件（GIVEN-WHEN-THEN）
1. GIVEN ... WHEN ... THEN ...
2. ...

### 异常分支
- {场景}：{预期处理}

### 数据约束
- {字段}：{规则}

### 涉及页面 / API
- 页面：/path
- API：METHOD /api/path

---

## REQ-{模块}-002：...
```

---

## 3. 用户门控

**呈现给用户的内容**：

1. 每个模块的需求清单（含来源标注）
2. 反推得到的需求需要逐条确认
3. 询问：
   - 「以下需求是否完整？」
   - 「是否有遗漏的场景需要补充？」
   - 「反推的需求是否准确？需要修改/删除哪条？」

**未获得用户对每个模块的明确确认，不得进入步骤 3。**

---

## 4. 边界情况

| 场景 | 处理 |
|------|------|
| 用户提供文档与代码冲突 | 标注冲突点，让用户裁定哪个为准 |
| 不同模块需求来源混合 | 在文档头部用 `MIXED` 标记，正文中每条标注实际来源 |
| 代码中存在不可达的入口（dead route） | 在反推时标注 `DEAD_CODE_SUSPECTED`，让用户判断是否纳入 |
| 项目无任何文档且代码极其复杂 | 仅反推核心模块（P0），其余推迟到下次迭代 |

---

## 5. 与下一步的衔接

本步骤产出的需求清单将进入步骤 3（需求评审）。评审会按 4 维度评分并填充覆盖矩阵——所以本步骤**不必追求评分高**，但**必须追求来源真实可追溯**。

宁可承认「这是从代码反推的，可能不准」，也不要伪装成「这是产品需求」。
