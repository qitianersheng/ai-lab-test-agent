# Step 1：测试用例设计

> **V0.10**：用户**上传**测试用例时以上传为准——AI 只**审核**不改写，把不合适处列「审核提醒」交用户，用户决定是否修改（见「上传用例审核」）。
> **V0.7**：用例产物 = 单个 Markdown 表格 `{任务}-testcase.md`（12 列见 `test-case-completeness.md §1.1`）；不再出 JSON / Excel。

## 前置检查

1. **任务名由本步自动生成**（语义优先、时间戳兜底，见下「任务名称生成」），**无需用户录入模块名**；用户若在 `$ARGUMENTS` 显式给了名字，则清洗为文件名安全 slug 后采用。
2. **必须**有用户提供的输入，三选一（由下「输入来源选择」交互确定，不自行从代码反推）：
   - 用户提供的**需求文档**（路径或粘贴文本：PRD / 设计稿 / 接口契约等）
   - **依据会话内容生成需求文档**（AI 回溯本轮对话提炼成文 → 用户确认 → 作为需求文档输入）
   - 用户直接提供的**测试用例**（清单 / 表格 / 描述）

## 输入来源选择（第一步 · 强制）

进入用例设计前，**先用 `AskUserQuestion` 让用户选择本轮输入来源**（不自行假设、不从代码反推需求）：

**问题：本轮测试用例从哪里来？**
- **我有需求文档** → 进入下文「需求文档导入」交互，引导用户把文档导入对话；AI 据此**分析并为「需求 × 适用维度」逐格生成用例**，默认预期依据标 `功能验证`。
- **依据会话内容生成需求文档** → 进入下文「会话内容生成需求文档」交互；AI 回溯**本轮对话上下文**提炼成一份需求文档、落盘、请用户确认；确认后视同「我有需求文档」逐格生成用例，预期依据按下文**逐条来源**判定。
- **我没有需求文档，直接给测试用例** → **以用户上传的用例为准（权威），AI 不改写内容**：只做格式归整（映射进 12 列表格、补 `TC-` ID），并对照完整性矩阵**审核**，把**不合适处列成「审核提醒」交用户**，由**用户决定是否修改**（详见下文「上传用例审核」）。不擅自新增、不臆造 预期依据。

### 需求文档导入（选「我有需求文档」后立即执行）

用户选了「我有需求文档」后，**主动发起一次导入对话**，明确请用户把文档给进来，并列出本客户端支持的导入方式（任选其一）：

> 📄 请把需求文档导入进来，支持任意一种：
> 1. **拖拽文件**到对话框，或点输入框的 **＋ / 附件**按钮上传（PDF / Word / Markdown / 图片等）
> 2. **@ 引用**项目内已有文件（如 `@docs/PRD.md`）—— 即「从已有需求文档中选择」
> 3. 直接**粘贴文档内容**到对话
> 4. 给出文件的**路径**（绝对或相对），我用 `Read` 读取

行为约定：
- **等用户真正把内容 / 文件 / 路径给进来后再继续**：给的是路径 → 用 `Read` 读取（PDF 多页用 `pages`；超大文档分段读）；给了多份 → 逐个读齐再设计。
- 用户暂未给 → 停在此步等待，**不**自行去代码或别处找需求。
- 读到后先**回显一句确认**（文档名 + 识别到的需求条目 / 章节数），再进入「任务名称生成」与用例设计。

### 会话内容生成需求文档（选「依据会话内容生成需求文档」后立即执行）

适用于：本轮对话里已和用户讨论过被测功能（业务规则 / 预期行为 / 验收点等），但用户手头没有成文 PRD。AI 把**已发生的会话内容**提炼成一份需求文档，作为用例设计输入。

1. **只回溯本轮对话上下文**提炼需求，**不**读外部日志、**不**扫代码反推（守 V0.4「不自说自话」红线）。提炼维度：功能点 / 业务规则 / 输入约束 / 预期行为 / 验收标准。
2. **逐条标注来源**（决定后续 预期依据，见 `test-case-completeness.md §1.6`）：
   - `[用户陈述]`：会话中**用户 / 产品明确说过的应然要求**（如「登录失败必须提示『账号或密码错误』」）。
   - `[AI推断]`：AI 依据代码 / 当前 UI 现状推断、用户尚未确认的条目。
3. **落盘**需求文档到 `AI_LabTest/testCase/{任务}-requirement.md`（任务名按下文「任务名称生成」从需求主题提炼）。每条需求含：编号、需求描述、来源标注（`[用户陈述]`/`[AI推断]`）、出处（引用会话里哪段）。
4. **用户确认门控（强制）**：把生成的需求文档呈现给用户，请其核对 / 补充 / 纠正，并对 `[AI推断]` 条目逐条裁定「是否为应然要求」。**用户确认前不进入用例设计。**
5. 确认后据该需求文档为「需求 × 适用维度」逐格设计用例；预期依据按 §1.6 逐条判定：`[用户陈述]` 或经用户确认升级的条目 → `功能验证`；仍为 `[AI推断]` 现状 → `回归基线`（**禁止**仅因写进需求文档就标功能验证）。
6. 用户不想生成 / 让 AI 别从会话提炼 → 退回输入来源选择，改走其余两条。

### 上传用例审核（选「直接给测试用例」后立即执行）

用户上传了现成用例时，**用例是权威，AI 只审不改**：

1. **格式归整（机械，不改内容）**：尽量保留用户原结构，映射进 §1.1 的 12 列表格、补 `TC-{任务}-{编号}` ID。缺的列**不臆造**——尤其「需求引用」(预期依据)，缺则在提醒里请用户补，**禁止 AI 编造**（§1.6）。
2. **审核（对照 `test-case-completeness.md §5` 完整性矩阵）**：逐条查结构 / 覆盖 / 断言 / 隔离，找不合适处，例如：必填列缺失、预期结果不可验证（「体验良好」类泛词）、操作↔预期不 1:1、缺 预期依据/验证性质、断言级别过低、覆盖维度缺口、隔离/顺序风险、ID 不规范。
3. **提醒（不替用户改）**：把发现列成一份「审核提醒」清单（逐条指明：哪条用例、什么问题、建议怎么改），呈现给用户。
4. **用户决定是否修改**：
   - 用户改了 → 按 V0.9「当前文件为准」**重新读取**当前用例，再审一遍；
   - 用户选择不改、按原样执行 → 尊重用户，照上传原样进入门控（提醒已留痕，风险由用户承担）。
5. AI **不擅自新增用例、不改写用户的测试逻辑/预期**；只在用户认可后才落定。

> - 选「直接给用例」但暂未给出 → 等用户给出用例后再继续。
> - 三者都没有 → **不进入设计**，提示用户先准备其一。

## 任务名称生成（自动 · 语义优先、时间戳兜底）

本步据输入自动确定一个**任务名（`{任务}`）**，作为本轮全链路（用例 / 执行结果 / 报告）的命名键与 `TC-{任务}-{编号}` ID 前缀：

1. 用户在 `$ARGUMENTS` 给了名字 → 清洗为文件名安全 slug（去空格 / 斜杠 / 特殊字符）后直接采用。
2. 否则从需求文档 / 会话提炼需求 / 现成用例中**提炼核心主题**，生成简短语义 slug（如「用户登录」→ `登录` 或 `login`；「订单创建」→ `order-create`）。slug 须文件名安全、尽量简短。
3. **兜底**：主题无法可靠判定，或同名 `testCase/{任务}-testcase.md` 已存在（冲突）→ 追加日期后缀 `-{YYYYMMDD}`（如 `login-20260618`）；仍冲突再加 `-{HHMMSS}`。
4. 生成的任务名在「用户门控」里一并告知用户，用户可要求改名。

## 规则
严格遵循 `${CLAUDE_PLUGIN_ROOT}/rules/test-case-completeness.md`（**先用 Read 工具读取该文件再执行**）。

## 来源 × 处理 × 默认预期依据（对照表）

承接上文「输入来源选择」，三种来源的处理方式与 默认预期依据：

| 来源 | 处理 | 默认预期依据 |
|---|---|---|
| 用户提供需求文档 | 为「需求 × 适用维度」逐格设计用例 | 功能验证（应然） |
| 依据会话内容生成需求文档 | 回溯对话提炼成文 → 落盘 `{任务}-requirement.md` → 用户确认 → 逐格设计用例 | 逐条判定：`[用户陈述]`/经确认升级 → 功能验证；`[AI推断]` → 回归基线 |
| 用户直接提供测试用例 | **以上传为准**：格式归整(映射 12 列、补 ID) + 审核 + 列「审核提醒」交用户裁定；**不改写内容、不臆造 预期依据、不新增** | 沿用用户标注；未标按 §1.6 判定 |

> 不再做代码库分析、三级回退需求发现、4 维度需求评审。照抄当前 UI 现状得到的预期只能标 `回归基线`（见 test-case-completeness.md §1.6）。会话提炼需求亦同此红线：会话内容若实为代码反推，只能回归基线。

## 执行步骤

1. 按上文「输入来源选择」用 `AskUserQuestion` 拿到用户选定的来源与内容（需求文档 / 会话提炼需求 / 现成测试用例）
2. 据输入按上文「任务名称生成」确定本轮任务名 `{任务}`
3. 生成用例：**有需求文档 / 会话提炼需求（已确认）** → 为每个「需求 × 维度」组合逐格生成（含判定表每条规则、状态迁移每个格 —— 见 test-case-completeness.md §2.1）；**用户直接给用例** → **以上传为准、AI 只审不改**：格式归整套进 12 列表格 + 对照矩阵审核出「审核提醒」交用户裁定（见上文「上传用例审核」），不改写内容、不臆造 预期依据
4. 每条用例 = 表格一行，含 §1.1 的 **12 列**（顺序固定）：
   `# | ID | 优先级 | 用例类型 | 模块 | 需求引用 | 用例标题 | 前置条件 | 测试操作 | 预期结果 | 断言 | 清理`
5. 关键列取值：
   - ID：`TC-{任务}-{编号}`；模块：本轮任务名 `{任务}`；用例类型：§2.1 八类之一；断言：L1/L2/L3/L4（§3.2）
   - **需求引用**列写 `<预期依据> · <验证性质>`（如 `PRD#REQ-001 · 功能验证` / `现状锁定 · 回归基线`）—— 预期依据 + 验证性质即落于此列，见 test-case-completeness.md §1.6
6. 对照完整性规则核验：结构 / 覆盖 / 断言 / 隔离
7. 在文档末尾输出「完整性检查」章节，列出每项核验结果

## 用户门控（强制）

> 若本轮走「依据会话内容生成需求文档」：用例门控之前**已有一道需求文档确认门控**（见上「会话内容生成需求文档」第 4 步），二者都要过。

使用 `AskUserQuestion`：
- **先告知本轮自动生成的任务名 `{任务}`**（用户可要求改名）
- 「以下 N 个测试用例是否可进入步骤 2（执行）？」
- 选项：全部采纳 / 调整后生成 / 跳过某些 / 补充某些
- **若本批用例全部为「回归基线」（预期依据 = 现状锁定）**：额外提示「这些用例只锁定现状、不验证正确性，是否补充权威需求来源（PRD / 产品确认）？」（见 test-case-completeness.md §1.6）

**用户未确认前，不得进入 Step 2。**

## 输出

- `/AI_LabTest/testCase/{任务}-testcase.md` —— **单个 Markdown 表格**，一行一条用例，12 列见 `test-case-completeness.md §1.1`；表后附「完整性检查」小节
- 仅「依据会话内容生成需求文档」来源时，额外产出 `/AI_LabTest/testCase/{任务}-requirement.md`（会话提炼并经用户确认的需求文档，供 预期依据追溯）

## 完成后的提示

> Step 1 完成。任务「{任务}」已生成 N 个测试用例，覆盖维度 X 项。下一步：运行 `/ai-lab-test:execute {任务}` 进入测试执行（AI 实时驱动 Playwright，无门控，自动执行）。
