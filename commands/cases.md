# Step 1：测试用例设计

## 前置检查

1. **必须**有模块名参数（`$ARGUMENTS`）；不填则提示用户补上
2. **必须**有用户提供的输入，二选一（缺失则向用户索取，不自行从代码反推）：
   - 用户提供的**需求文档**（路径或粘贴文本：PRD / 设计稿 / 接口契约等）
   - 用户直接提供的**测试用例**（清单 / 表格 / 描述）

## 规则
严格遵循 `${CLAUDE_PLUGIN_ROOT}/rules/test-case-completeness.md`（**先用 Read 工具读取该文件再执行**）。

## 输入来源（V0.4 · 用户驱动）

| 来源 | 处理 | oracle 默认 |
|---|---|---|
| 用户提供需求文档 | 为「需求 × 适用维度」逐格设计用例 | 功能验证（应然） |
| 用户直接提供测试用例 | 结构化、补齐必填字段、对照完整性矩阵核验缺口 | 沿用用户标注；未标按 §1.6 判定 |

> 不再做代码库分析、三级回退需求发现、4 维度需求评审。照抄当前 UI 现状得到的预期只能标 `回归基线`（见 test-case-completeness.md §1.6）。

## 执行步骤

1. 读取用户提供的需求文档**或**现成测试用例
2. 为每个「需求 × 维度」组合生成测试用例（含判定表每条规则、状态迁移每个格 —— 见 test-case-completeness.md §2.1）；用户直接给用例时则结构化并补齐字段
3. 每个用例必须包含 6 必填元素：
   - 目的 / 前置条件 / 测试操作 / 预期结果 / 预期结果来源（oracle）/ 清理
4. 每个用例必须标注：
   - ID：`TC-{模块}-{编号}`
   - 用例类型：§2.1 八类覆盖维度之一
   - 断言级别：L1/L2/L3/L4
   - oracle 来源 + 验证性质（功能验证 / 回归基线）—— 见 test-case-completeness.md §1.6
5. 对照完整性规则核验：结构 / 覆盖 / 断言 / 隔离
6. 在文档末尾输出「完整性检查」章节，列出每项核验结果

## 用户门控（强制）

使用 `AskUserQuestion`：
- 「以下 N 个测试用例是否可进入步骤 2（执行）？」
- 选项：全部采纳 / 调整后生成 / 跳过某些 / 补充某些
- **若本批用例全部为「回归基线」（oracle = 现状锁定）**：额外提示「这些用例只锁定现状、不验证正确性，是否补充权威需求来源（PRD / 产品确认）？」（见 test-case-completeness.md §1.6）

**用户未确认前，不得进入 Step 2。**

## 输出

`/AI_LabTest/testCase/{模块}-testcase.md`

## 完成后的提示

> Step 1 完成。{模块} 已生成 N 个测试用例，覆盖维度 X 项。下一步：运行 `/ai-lab-test:execute {模块}` 进入测试执行（AI 实时驱动 Playwright，无门控，自动执行）。
